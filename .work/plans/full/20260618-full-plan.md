## 1. Executive Summary

tools-project is a project management hub evolving into a unified PM + CRM product. The internal tool foundation (projects, tasks, tickets, activity, GitHub sync) is built. Remaining work splits into two tracks: (A) complete the GitHub integration front-end, and (B) add CRM features — client companies, contacts, sales pipeline, and limited client project access. This plan defines 4 milestones for the remaining scope, with M1 (CRM schema + prospects) as the first execution target.

**Top risks:** Permission boundary isolation between internal members and client participants; Batch I vs J priority conflict; missing GitHub PAT environment setup friction.

---

## 2. Project Goals

- **G1:** Internal team can complete daily PM workflows (tasks, tickets, activity, GitHub integration) from the web UI, not just the API.
- **G2:** Sales team can manage a prospect pipeline from lead intake through closed-won/lost.
- **G3:** Client stakeholders can view project status, tasks, and public activity without internal tool access.
- **G4:** Permission isolation between internal `project_members` and client `project_client_access` is auditable and enforceable.

## 5. Constraints

- **No Alembic** — all schema changes are idempotent `sql/schema_*.sql` files run at API startup.
- **Docker-only** dev environment — Contributors must have Docker; no host Node/Python installs.
- **Dual auth mode** — local JWT and/or OAuth; client login uses a separate page but the same auth backend.

## 9. Architecture Overview

Single-monolith FastAPI + Next.js application (see foundation doc 04 for bounded context diagram). Key boundaries:

- **API:** `api/app/routers/` — one router per bounded context (projects, tasks, tickets, activities, github, prospects, clients).
- **Web:** `web/src/app/` — Next.js App Router routes mirroring API endpoints; `/client/` route group for client portal.
- **DB:** PostgreSQL 16 with SQLAlchemy 2 async; all new CRM tables use the same pattern (`sql/schema_changes.sql`).
- **Auth:** Shared JWT/OAuth infrastructure; client auth reuses the same `get_current_user` dependency with a different login UI path.

---

## 10. UX/UI Strategy

- Internal UI unchanged — existing AppShell, Today, Projects, Inbox, ⌘K remain as-is.
- Client portal lives under `/client/` route group with a separate layout (no AppShell, limited navigation).
- `/client/login` is a minimal login page distinct from `/login`.
- Client dashboard shows: list of accessible projects, per-project task/ticket overview, public activity feed.
- Pipeline management under `/prospects/` and `/clients/` — internal-only routes.

---

## 11. Data Strategy

- Existing tables: `users`, `projects`, `project_members`, `components`, `tasks`, `activities`, `tickets`, `attachments`, `inbox_items`, `watchers`, `github_links`, `github_commits`.
- New tables: `prospects`, `clients`, `client_contacts`, `project_clients`, `project_client_access` (plus optional `client_referrals`, `client_onboarding_items`).
- `clients` auto-created when prospect transitions to `won` (transactional).
- `project_client_access` enforces the hard permission boundary — no role-based override to bypass `is_internal` filtering.
- Attachment storage remains local filesystem (V1); S3 upgrade path documented but not scheduled.

---

## 12. Security Strategy

- All new API routes require authentication via `get_current_user` (local JWT or OAuth).
- `project_client_access` permission checks happen in `deps.py` alongside `project_members`.
- `is_internal = false` activity filter applied server-side for client participants.
- Client JWT tokens use the same signing infrastructure as internal tokens, with a `token_typ` claim for potential differentiation.
- No secrets in git. GitHub PATs encrypted with Fernet at rest.

---

## 13. Infrastructure Strategy

- Docker Compose remains the single dev environment (3 services: postgresql, api, web).
- No changes to compose file for CRM additions — all new code lives within existing containers.
- `.env.example` extended with any new environment variables (none required for CRM V1).
- Production deployment path unchanged (no production environment defined yet).

---

## 14. Deployment Strategy

- Schema changes are applied on API startup — no separate migration step.
- New tables use `CREATE TABLE IF NOT EXISTS`; new columns use `ADD COLUMN IF NOT EXISTS`.
- Backward compatible: existing projects and users are unaffected by CRM additions.
- Client routes (`/client/*`) are new Next.js route group — no changes to existing routes.

---

## 15. Scalability Strategy

- CRM additions add modest data volume (prospects, clients, contacts at most thousands per org).
- `project_client_access` permission checks add at most one additional query per request — negligible overhead.
- The existing monolith architecture is sufficient for single-org deployment at current scale.

---

## 16. Observability Strategy

- New API routes follow the existing logging pattern (structured logging in router handlers).
- Prospect pipeline transitions should emit audit-log entries in `activities` table with `kind` prefix.
- Client access grant/revoke should be logged as activities with `is_internal = true`.
- No new metrics or traces required for CRM V1 beyond existing SSE activity stream.

---

## 17. Testing Strategy

- API: pytest for route handlers, SQLAlchemy model unit tests.
- Permission resolution (`deps.py`) must have dedicated test coverage for the `project_members` + `project_client_access` dual check.
- Web: existing pattern of `npm run check` (TypeScript + lint) and `npm run build` (production build).
- Idempotency: `apply-ddl` run twice in CI must produce same schema.
- No e2e test framework defined — manual smoke testing for client portal.

---

## 18. Operational Strategy

- DDL idempotency ensures restart-safe schema application.
- Client login failures and unauthorized access attempts logged at WARNING level.
- Pipeline stage transitions are idempotent (PATCH with validation, not state machine side effects).
- No new background jobs or cron for CRM V1.

## 22. Rollback and Recovery Considerations

- All schema additions are additive (`CREATE TABLE IF NOT EXISTS`, `ADD COLUMN IF NOT EXISTS`) — safe to deploy and revert by simply not using new features.
- Prospect-to-client promotion on `won` is transactional — if client creation fails, prospect stays at current stage.
- Client access grants are row-level — revoke is a DELETE from `project_client_access`.

---

## 23. Technical Debt Prevention Strategy

- Permission boundary in `deps.py` must remain a single well-documented function — any future expansion (e.g., multi-tenant) should replace, not patch around it.
- `/client/login` route group must not import internal-only helpers — keep client portal code in `web/src/app/client/` and `web/src/components/client/`.
- New models follow the existing SQLAlchemy declarative pattern — no custom base classes.

## 24. AI-Agent Execution Guidance

| Constraint | Rule |
|------------|------|
| Permission boundary | **Never** add `project_client_access` data to `project_members` queries or vice versa — separate tables, separate checks |
| DDL idempotency | Every new table/column must use `IF NOT EXISTS`; verify by running `apply-ddl` twice |
| Client login | Must use a separate route group (`/client/`) — do not modify `/login` or internal layouts |
| Client data isolation | Client participant route handlers must filter `is_internal = false` server-side — do not rely on client-side filtering |
| Model-tier hints | M1-T1..T6 (schema): `light`; M1-T8..T9 (API): `standard`; M3-T4 (permission): `strong` — cross-model review recommended |
