## 1. Executive Summary

Mendarion is a multi-tenant clinical platform with three planes of data: a **practice tenant store** (**ADR 018 hybrid placement**: schema-isolated RLS pool for practice/SMB tenants, dedicated database/instance for enterprise/compliance-sensitive tenants; the demo runs one DB per tenant), a **patient plane** (a dedicated consumer store holding the patient-owned master record) and a **PHI-free platform store** (tenant registry + the public practitioner directory index). The product serves **professionals, clinics, pharmacies, patients/consumers and hospitals** (A30) — a consumer who signs up directly is **never a tenant** (they belong to the patient plane); the tenants are **doctors, clinics, pharmacies and hospitals**, each holding its own store for its records, its data and the patient data it generates. The first deliverable is an **internal 2-week synthetic demo** (D-S3, U28): the revision-1 practice loop **plus** a minimal consumer path — public signup → directory browse → master file → one share grant → the clinician opens the shared file.

Twelve milestones: **M1** platform skeleton (three stores, control plane, no features) → **M2** identity & assurance → **M3** consumer record + public directory → **M4** sharing & grants → **M5** the practice loop → **M6** Rx-lite → **M7** demo hardening and the acceptance run (**M1–M7 = the demo**), then the owner-fixed staged order: **M8** AI routing + Sentinel, **M9** practice self-service, **M10** live telehealth, **M11** virtual pharmacy, **M12** enterprise tier + pilot readiness.

**Top risks:** R24 (patient-facing routing is regulated triage — H/H, gated on U15), R27 (consumer identity + cross-practice sharing — H/H), R30 (Sentinel alert fatigue/missed risk — H/H), R13/MOD-04 (solo capacity; the revision adds a second database class and an object store), R19/U18 (no UI foundation exists yet — the largest delivery unknown; the owner will provide the UI Foundation Plan before implementation starts), R33 (media in the tenant store changes the backup story), R34/R35 (model drift and test rot eroding the contract layer), **R37 (generated code under-enforced until the M1 gates land — closed by D14)**. **No milestone past M1 requires a decision that is not already Decided** — the hybrid tenancy model is now Decided (ADR 018) — but **M8, M10 and M12 are hard-gated** on U15, U29 and U13/U33 respectively, and **nothing is implemented before its SPEC is Approved**.

Records with **no** retention obligation are **deleted**. Records inside a retention window or under a legal hold are **de-referenced, not anonymised**: their identifiers are removed by the **versioned identifier scan** (`identifier_set_version`) and the rest of the record — including the patient's verbatim narrative — is **retained in full for its window**, and the row **keeps its class** (a scrubbed `feedback_items` row is still C4). It is **hard-deleted** when the window expires or the hold is released. **Why not "anonymised":** for narrative and C4-derived rows that claim is not provable — redaction is *risk reduction, not de-identification* (`data-classification` §5) — and HIPAA de-identification would need an **Expert Determination** this repo does not have. **So the bar is identifier-based, not class-based: `erasure_residual_identifiers_total` = 0**, not "zero residual C3/C4 rows". Every action is marked (`erasure_marker` = `deleted` or `de-referenced`, plus `acted_at` + `identifier_set_version`), so the assertion cannot be satisfied by absence. **The patient is notified** — what is retained, under what duty, and when it is finally deleted (`erasure_notices_sent_total`); a silent partial refusal is a defect, not a compliant outcome. **The request is routed per controller:** the patient-plane master file is the patient's own and is actioned directly; the **tenant-held portion is *requested*, never seized** — the practice is an independent controller of a record it holds under a medical-record retention duty and may lawfully refuse, which it records and the patient is told. **Who decides the mechanism:** the platform's per-class retention policy (config-driven, `A51`) — never the requesting patient, never the tenant ad hoc. **Objects are not anonymised, they are unlinked.** A `C4-v` recording/transcript or clinical document cannot be irreversibly anonymised — blurring is reversible and re-synthesis is not the same artefact — so the "anonymise" outcome for an object means **destroy the identifier link, never modify the bytes**: the pointer row (`recording_ref`, `document`) is deleted and the blob re-keyed under an opaque id, or the blob is deleted outright when no obligation is owed. The object residual assertion is therefore **zero un-linked objects**, not "zero anonymised". **The rule is `D21`**, with its rejected alternatives. **Who decides:** the platform's per-class retention policy (config-driven, `A51`) — never the requesting patient, never the tenant ad hoc. A **legal hold** is a *registered, audited* flag owned by the platform operator (`legal_hold`: person ref, reason, window, set-by/released-by) — never something a tenant or a patient asserts; **U13 supplies the windows and the hold list**. `M2-T14` must write this precedence as numbered rules **before `M5-T16` builds the runner**. **Scope:** the run covers the **tenant store, the patient plane, the platform store and their objects**; it is **idempotent**; it leaves an audit trace of the erasure itself (no clinical content). **An erasure also revokes the subject's grants and consents** and removes the patient-plane `grant`/`grant_resolution` rows naming them, so an erased subject is no longer resolvable as grantor or grantee (ADR 014) — while the **append-only `audit_events` trail survives untouched** (C1, never pruned, `NFR16`): the patient-plane rows are patient-owned and go; the provider's record of *having accessed* the record does not. `audit_events`, `erasure_run` and `data_subject_request` are therefore **exempt from the residual assertion and are the evidence for it**. **Proved, not claimed:** by a residual-assertion test and the **`M7-T9` drill**. Account closure continues to block access immediately (`consumer-onboarding` R13) and *starts* this workflow; the export is delivered as a short-lived signed bundle through the same ownership/grant rules, so it can never become the sanctioned cross-plane copy ADR 014 and U35 forbid | `data-classification` §4 (the pre-existing binding requirement, previously unwired) · ADR 011/014 · **A51** · SPEC `data-subject-rights` (**authored at M2-T14**) |

A critical goal of the system is to **make the clinician's work easier** — simplification of clinical tasks is of great importance for the application's success (owner developer notes, §3). Every FR and every milestone's UI work is measured against **G7**.

**The three invariants** (doc 04 §1, all test-asserted): tenant scoping at the data-access layer; **no raw PHI crossing a plane boundary**; **every cross-store read passes the grant service**.

## 11. Data Strategy

- **PostgreSQL 17, three plane roles** (ADR 002 + **011** + **018**): **tenant store** — practice/SMB tenants default to the **schema-isolated pool** (one database, one schema per tenant, RLS inside), enterprise/compliance-sensitive tenants get a dedicated database/instance; the demo runs one DB per tenant (a pool of one). Placement is a tenant-registry attribute resolved by `shared/tenancy.py`; moving a tenant between placements is copy → verify → cutover. **patient plane** — a dedicated consumer store with per-person isolation (no `tenant_id`); **platform store** — PHI-free, holds the tenant registry and the public directory index.
- **Scale-out-readiness schema conventions** (ADR 018 §4, codified in `CONVENTIONS` §12): `tenant_id NOT NULL` leading on every tenant-scoped table and leading in composite indexes; no tenant-scoped query omits a `tenant_id` predicate; UUIDv7 (or composite) ids, no global `SERIAL` as the sole tenant-scoped primary key; no cross-tenant FKs; per-tenant observability (rows written, p95 query latency, connections) from the first deployment.
- **Entities:** doc 04 §6 (per plane); **classification:** `20260924-data-classification.md` §3 tags every revision-2 table, and the public index has a **build-failing** rule against an unclassified field.
- **Migrations:** numbered, idempotent SQL under `apps/api/migrations/`, applied **per store** by `mendarion.shared.migrate` at boot, in order; runners are verified by running twice on a dev database; destructive statements need same-message owner approval.
- **Retention/erasure:** 7 years clinical (and recordings) by default via **storage lifecycle rules** for objects (NFR17); erasure spans all three stores and their objects (U13 finalises the windows).
- **No copies across planes** (U22/ADR 014) — sharing is grants resolved at read time. **Record-partitioning rule (owner developer notes, 2026-09-26):** the tenant seeing a patient **keeps the part of the record it generated** (prescriptions, notes, follow-ups, transcripts, meeting references); the patient's master file is reached by grant, never materialised. A tenant copying "minimal data" from the patient plane — or from another tenant — **is not sanctioned by this plan**: it would be a snapshot copy requiring an ADR 014 amendment plus a retraction/erasure mechanism; that question is tracked as **U35** (currently: no).
- **Search:** Postgres full-text in the tenant store for feedback; the directory index is a projected, allowlisted table (ADR 013 §8).
- **Customization (ADR 020 §2):** tenant definitions live in the **tenant store** — a **JSONB body inside a relational envelope** (`definition`/`definition_version` with `tenant_id` leading, version, state, classification, `canonical_map`), validated against a platform-owned **meta-schema** at publish, append-only per version, ≤ 256 KB; **no separate document store** (the ADR's alternative table records why). Definitions follow the tenant's placement; instances pin the version they were created under.
- **Translation (ADR 021 §Decision 4):** the localised text lives in **`localised_string`** (one row per string per locale) beside `glossary_entry` and `translation_job` — so provenance, review state and the render fallback are **per-string facts**, and a published string is a stored value that renders without any live model call.

## 12. Security Strategy

Threat model: `20260924-threat-model.md` (revised for revision 2 — boundaries **T1–T10**, assets A1–A8c, STRIDE extended). Controls in force from M1:

- **AuthN/AuthZ:** staff email+password+MFA; consumer accounts with contact verification and **assurance levels L0/L1/L2** (ADR 012); tenant context from **membership**, plane context from the request's plane — never from a parameter (api-style-guide §2).
- **Isolation:** data-access-layer scoping + RLS per tenant DB + per-person scoping in the patient plane; the **grant service is the only cross-plane path**; a `directory` projection is one-way, field-allowlisted and classification-tested.
- **PHI egress:** one adapter (BC5), fail-closed redaction, contract at U14; transcripts keep the same rule. **Notification channels are egress points too:** every send goes through `shared/notify.py`, bodies are locale-templated with no free-text PHI, and sends are counted/audited (`notification_sent_total`); WhatsApp/Signal/Telegram/SMS stay disabled until U37 (R36).
- **Secrets:** environment only; `.env.dev`/`.env.prd` git-ignored; stub verification channels **boot-guarded out of `prd`** (consumer-onboarding I5). **Staged (M12-T11):** encrypted, DB-backed runtime overrides may override a **defined allowlist** of hot-reloadable, non-credential values so a stack/service restart is avoided — credentials and keys are never overridable. **Store split (ADR 020 §3 — corrected 2026-09-27):** the overridable set is split by classification — **toggles/entitlements/limits** (non-clinical) may be overridden in the **platform store**; **thresholds and rule values are clinically meaningful (C1)** and are tenant-store definitions owned by BC14, never platform-store overrides.
- **PHI egress — translation is an egress point too (ADR 021/022):** **only non-patient-facing** tenant copy is translated, by the `translate_content` job through the **same single adapter** (BC5, `ADR 005`), after the **same deterministic identifier scan** as redaction; a hit means **no provider call** and the string is marked `needs_manual_translation`. A patient-facing string is **refused before egress** (`translation.patient_facing_forbidden`), a machine draft may never be published where the review gate requires a human (`R29`), and no source or target string may appear in a metric label, span attribute, log line or error body (`NFR8`, `NFR20`).

## 15. Scalability Strategy

- **Pilot envelope:** 1 clinic, ≤10 clinicians, ≤5k patients, ≤50k check-ins/year, K–M rows per tenant (doc 04 §5). No horizontal scaling claim is made for the demo.
- **Hybrid placement (ADR 018):** SMB tenants pool into a schema-isolated database; enterprise/compliance-sensitive tenants get dedicated stores; a tenant moves between placements by re-routing its connection spec. The pool and PgBouncer-class pooling land pre-pilot (M12-T13).
- **Named seams:** (a) the tenant-store placement seam is `shared/tenancy.py` (connection-spec per tenant — pool or dedicated, ADR 018); (b) **the patient plane's per-person store dimension** — a capacity note is required before the pilot (the P3 review's finding); (c) the AI worker is decoupled via Redis Streams so provider latency never blocks a request.
- **Day-one scale-out-readiness rules (owner developer notes, 2026-09-26 — binding from M1):** (1) **shard key in schema** — `tenant_id NOT NULL` leads every tenant-scoped table and composite index; no tenant-scoped query omits a `tenant_id` predicate; a sharding strategy that creates shards automatically is preferred, and the recommendation is an **in-house sharding strategy** over third-party plugins; (2) **stateless app tier** — sessions in Redis/JWT, uploads in object storage, caches external, background jobs in a durable queue; killing any instance mid-request loses nothing; (3) **id strategy** — UUIDv7 or `(tenant_id, local_seq)`; no global `SERIAL`/`AUTO_INCREMENT` as the sole primary key on tenant-scoped tables; (4) **no cross-tenant FKs** — cross-tenant lookups are explicit and flagged; (5) **externalised config & infra** — PgBouncer-class pooling, all config via env, logs/metrics to a central collector; (6) **per-tenant observability** — rows written, p95 query latency, connection count per tenant from the first deployment (shard-placement input). **Out of scope until scale-out:** multi-node DB, shard router, read replicas, load balancer — deferred and expected to be straightforward ops changes given the above.
- **Caching:** tenant-scoped aggregates + medication lookups behind `shared/cache.py`; grant-resolution caching with a **sub-5 s TTL** + invalidation broadcast (ADR 014). U19 reviews whether the cache earns its place.
- **Queues:** Redis Streams with consumer groups, leases and dead-lettering; a job table remains the system of record.
- **The public directory** is the one surface that may be cached aggressively (public content, no session, CDN-friendly).

## 17. Testing Strategy

- **Levels:** unit (`pytest`, vitest) · integration against **real containers** for all three stores (testcontainers) · API contract (OpenAPI diff) · e2e/a11y (Playwright: patient check-in, consumer sign-up→share, clinician triage, directory browse) · migration idempotency (run twice) · load smoke (p95 assertions for NFR1–NFR3, NFR11–NFR13) · **schema-convention tests** (leading `tenant_id`, no global-SERIAL PK, no cross-tenant FK — CONVENTIONS §12) · **architecture checks** (import boundaries per DIRECTORY_MAP §3 via `import-linter`; clone detection via `pylint duplicate-code` failing on ≥5 duplicated lines) · **property-based tests** (`hypothesis`) for the three invariants and redaction (QUALITY_GATES §5.2) · **mutation testing** (`mutmut`) on the dangerous paths, automating the R35 sweep (QUALITY_GATES §8) · **test-health review** (flake rate, critical-path coverage drift, "test that never fails" sweep — §25, R35).
- **Rule-driven:** every SPEC R-rule has a named test in its §11; a PR lists the R-rules it implements.
- **Cross-cutting invariants get a gate, not a one-off test** (2026-09-27): the **locale/key-parity test runs on every UI task**, not only at `M1-T10` — FR23/NFR10 claim *all* copy lives in locale files and *both* locales ship, which is a claim about every screen in eight later milestones, so a one-time M1 test cannot carry it. The same applies to the a11y baseline, the JS budget and the schema-convention tests.
- **Latency budgets are asserted as worst cases** (2026-09-27): a hard bound (revocation ≤ 5 s) is proved by its **worst case**, including the degraded path (the invalidation broadcast dropped, only the ≤ 2 s TTL backstop). A p95 assertion cannot evidence a maximum, and the NFR12 budget is now split so the components provably cannot sum past the bound — broadcast p99 ≤ 1 s · TTL backstop ≤ 2 s · remainder (clock skew + path overhead) **≤ 1 s**, so the worst case (broadcast lost) is 3 s against a 5 s bound.
- **Security tests that must exist before the demo:** cross-tenant read returns zero rows; **cross-plane read without a grant is denied** (and no foreign-plane content is persisted); redaction failure blocks egress **and makes no provider call at all** (an absence assertion — QUALITY_GATES §5.3); **no PII in logs/traces** (capture scan); **the directory index has no clinical column**; grant revocation **worst case ≤5 s against an injected clock, never a sleep** (QUALITY_GATES §5.4), including the lost-broadcast path; the stub verification channel refuses `prd` boot; **an erasure leaves zero residual identifiers and zero un-linked objects in all three stores, a re-run is a no-op, an export contains only the patient's own data, the patient notice is emitted, and a narrative row is de-referenced rather than deleted** (FR28/NFR21 — a deletion claimed but not performed is a reportable breach, and a partial erasure performed *silently* is its own failure, so both are asserted, not reviewed).
- **Every trust boundary has a negative test** (§12's control-coverage matrix): `T1`–`T10` each name an enforcing task and the test that proves the control, and `M12-T10`'s pre-production scan re-walks that matrix — a boundary closed by "the code is careful" is not closed.
- **Coverage target:** **rule coverage** stays the primary gate (every R-rule mapped to a test) plus the security list above — with **one exception**: the modules on the §24 dangerous-path list carry a **≥95% branch-coverage floor** enforced per module (QUALITY_GATES §5.1). A global percentage would hide a missed branch in `shared/tenancy.py`; a per-module floor cannot.
- **Enforcement starts at M1.** Hosted CI is deferred to M12-T2 (U2, D7); **gate enforcement is not** (D14). Every gate below runs locally, in-container, through the aggregate **`./bin/start.sh verify`** verb from the first implementation milestone, and M12-T2 wraps that same stage list so the pipeline cannot drift from the local gate (QUALITY_GATES §2).
- **Schema drift is a test, not a convention:** `pytest -m schema_drift` applies the full migration chain and diffs the resulting schema against the SQLAlchemy metadata — the executable form of §11's "SQL is the source of truth" (QUALITY_GATES §6).

### 19.1 The task acceptance contract

Every task row in §19 carries an **`Acceptance`** cell: *one observable condition* — a behaviour, a number, a named test, or a named absence. It was added on 2026-09-27 because the tables previously ended at `Status`, which made a task's done-condition a matter of interpretation at execution time across 153 slices.

The rules that make it binding:

1. **A task is not done until its `Acceptance` cell is observably true** and `./bin/start.sh verify` is green (§21). Status moves to `done` only with the evidence, not before.
2. **The cell is the contract, not a summary.** If implementation forces a change, the cell is amended in the same change that amends the code — a task may not quietly ship something its acceptance cell does not describe.
3. **Prefer a negative assertion.** "A cross-tenant read returns zero rows" and "a redaction failure makes **no** provider call" are the shape; "the code is correct" is not an acceptance condition.
4. **Absence is assertable.** Where the guarantee is that something must *not* exist or must *not* be called (no dispensing code, no vendor storage, no PHI in Redis, no machine translation reaching a patient), the cell names the scan or the absence assertion that proves it.
5. **A task whose acceptance cannot be written is not ready to be planned.** That is the signal to split it — which is why the three un-schedulable mega-tasks (`M1-T20`, `M9-T8`, `M9-T9`) were decomposed on 2026-09-27 into `M1-T20…T23`, `M9-T8/T10/T11` and `M9-T9/T12/T13/T14`. Task ids were **appended, never renumbered**, so every cross-reference in the registries, ADRs and SPECs still resolves.
6. **The `code-implementation` iteration block in `NEXT.md` restates the acceptance cell** for the task being executed, and records the evidence in the task's `Notes`.

**Known limitation, stated rather than hidden:** the plan carries **no effort estimate, no schedule and no capacity model** (deliberately out of scope for the 2026-09-27 audit). The `Acceptance` column therefore says *what must be true*, never *how long it takes* — so R13 (solo capacity, H/H) is still unquantified, and that remains the plan's largest open weakness.

## 20. Acceptance Criteria (global)

- **The demo:** all six items of doc 01 §Demo acceptance pass on a fresh seeded stack, with evidence, and the S4 journey is timed ≤10 minutes unaided. (M1–M7)
- **Isolation:** a cross-tenant read and a cross-plane read without a grant both return zero rows in every test suite; RLS is present in every tenant DB; **the schema-convention tests (CONVENTIONS §12) pass** — leading `tenant_id`, no global-SERIAL sole PK, no cross-tenant FK. (NFR6, ADR 018)
- **PHI discipline:** no un-redacted egress; no PII/PHI in telemetry; the public index has no clinical column. (NFR7/NFR8/NFR18)
- **Sharing:** revocation effective ≤5 s, measured; the access log is patient-only. (NFR12, FR5)
- **AI discipline:** provenance on every output; no autonomous clinical write; each job type enabled only after its evaluation bar. (G4)
- **Operability:** every routine operation is a control-plane verb; a verified restore drill covers all stores and objects; `env-check` holds the three env files in **1:1 key-set parity** (line correspondence is the authoring requirement); per-tenant ops metrics are live from M1. (G6, NFR5, ADR 018)
- **Staged honesty:** no shipped copy claims a capability that has not been built (no network prescribing claim before V3; no patient-facing Sentinel copy before U15).
- **Data rights (FR28/NFR21):** erasure is **identifier-based** — `erasure_residual_identifiers_total` = 0 and zero un-linked objects across **all three stores** — is **marker-based** (every action recorded, so the count is falsifiable rather than assumed), is idempotent, is audited with no clinical content, and is proved by the **`M7-T9` drill with filed evidence**, not asserted. A record inside a window or under a hold is **de-referenced and retained in full — narrative included, class unchanged — then hard-deleted on release/expiry**; "anonymised" is not claimed for it. **The patient is notified**; the tenant-held portion is **requested, never seized**; **`audit_events` survives**; grants and consents are revoked; and **no normative wording** anywhere claims zero residual C3/C4 rows — superseded mentions survive only as dated records (the `D21` cell's head banner, `A51`'s log entry, `NEXT`'s Done log, the observability changelog) and each is marked as superseded; the export contains only the patient's own data and travels the same ownership/grant rules; and no retention or erasure window is hard-coded. Account closure still blocks access immediately (`consumer-onboarding` R13) **and** starts this workflow.
- **Customization discipline (FR26):** no hook outside the catalogue resolves; a declared hook has a wired consumer; no definition weakens an immutable of ADR 020 §11 (the reserved-area test passes); four-eyes is enforced **server-side** for safety-relevant or C2+ definitions; a practice-held answer is never returned by grant resolution; BC14 reads no clinical table (import contract).
- **Translation discipline (FR27):** **no machine-translated string is ever rendered to a patient** (ADR 022 — a patient surface renders the selected locale or the definition's default); the structural guarantees hold on the `EN ⇄ ES` set (placeholders preserved · no new numeric token or unit · no chained MT · non-empty); an unreviewed required-locale string blocks publish; every definition write and every translation job is audited; the identifier scan fails closed with **no provider call**.

## 22. Rollback and Recovery Considerations

- **Feature flags are the primary rollback:** every new surface ships behind one (`consumer.signup`, `directory[.listing|.sponsored]`, `sharing[.residency.strict]`, `checkin`, `assist.*`, `rx.lite`, `live`, prescribing-per-tenant, `notify.channels.*`). Their **fail-closed directions** are documented (e.g. `sharing.enabled=false` denies all cross-plane reads). **Verification (owner developer notes, 2026-09-26):** every flag-based rollback is followed by a **flag-off smoke** (the surface returns its documented off state) before the incident closes.
- **Migrations are additive and idempotent**; a breaking change is two-step (expand → migrate → contract). Destructive statements require same-message owner approval and a documented plan (`.cursorrules` §Database). The **expand → migrate → contract** sequence is rehearsed on a dev database before any breaking change ships.
- **The directory index and the projections are rebuildable** from the owning stores — a rollback path that data in a tenant store does not have. The **rebuild path is exercised as a test** (M3-T13), not described as one.
- **Store-level recovery:** per-store backups + verified restore (NFR5); a restore drill is a **milestone acceptance item**, not an afterthought (M7-T6). The drill restores **all three stores and objects** and then runs the flag-off smoke.
- **Placement rollback (ADR 018):** moving a tenant between the pool and a dedicated store is copy → verify → cutover in both directions; the reverse direction is rehearsed in the M12-T13 drill.
- **Environment rollback:** the three env files are text, 1:1 line-correspondent by authoring requirement and `env-check`-validated for **key-set parity** — reverting an env change is a file restore plus the parity check.
- **The tenant is disposable in the demo:** `nuke` → `up` → seed (`reset` is the full-stack reset).
- **Per-milestone rollback** is recorded in each milestone block above.

## 23. Technical Debt Prevention Strategy

- **Refactor pressure points (named now, not later):** (a) `shared/planes.py` + `shared/db.py` will accumulate plane logic — keep them interface-only and tested; (b) the grant resolver's cache correctness is a privacy-critical coupling — the TTL-invalidation invariant is asserted, not assumed; (c) the projection mapper is the boundary that keeps the public store PHI-free — every added field needs a classification review; (d) the AI prompt/output contract grows per job type — keep `prompts/` versioned and immutably referenced by suggestions; (e) `shared/notify.py` must stay the **single** notification path — a second send path is a defect.
- **Debt ledger policy:** debt is recorded as a `RISK_REGISTRY` entry or a SPEC open question with an owner — never as a code comment alone. A milestone cannot close with an unowned `TODO` in `src/`.
- **The demo-divergence policy:** every demo shortcut (mock verification, no CI, stub provider, minimal UI) is recorded with the milestone that replaces it — so "temporary" has an end date.
- **No drive-by refactors:** `.cursorrules` forbids collateral edits; scope is declared per task.
- **Technical-debt prevention mechanisms (owner developer notes, 2026-09-26 — binding for agent-authored work):** (1) **spec-driven development** — the SPEC defines function signatures, expected inputs/outputs, edge cases, performance constraints and which existing utilities to reuse **before** the AI is asked to implement; (2) **context engineering** — the agent is fed the architecture context (interface contracts, linter config, ADRs, relevant module functions) so it imports existing helpers instead of cloning them; (3) **contract enforcement** — machine-checkable schemas (Pydantic, Zod, OpenAPI) turn assumptions into runtime-validated contracts and block drift in CI; (4) **architectural boundary enforcement** — ALLOWED_IMPORTS-style rules fail builds when code crosses the DIRECTORY_MAP §3 boundaries; (5) **duplication prevention** — AST-based clone detection blocks merged blocks of ≥5 duplicated lines, and the "do we already have this?" check is part of the per-task contract; (6) **traceability** — living SPECs keep bidirectional intent↔implementation linkage so divergence triggers a build failure, not silent accumulation; (7) **governance** — 15–20% of iteration capacity is reserved for refactoring, the refactor-to-add ratio is tracked, architecture reviews run quarterly, and any AI-authored architectural or security-boundary code requires human review before merge.

## 24. AI-Agent Execution Guidance

- **Read before writing:** `.cursorrules` → `DIRECTORY_MAP` §2/§3 → the SPEC for the context → `CONVENTIONS` → the observability spec for the signals.
- **Reuse-first (no duplicate paths):** before writing a helper, service or query, check `shared/` and the context's `service.py` — a second path doing the same thing is a defect (§9, §23 mechanism 5); notification sends go through `shared/notify.py` only.
- **Dangerous paths (require explicit care and a test):** `shared/{db,tenancy,planes}.py` (isolation + placement), `sharing/resolver.py` (read-time resolution + revocation), `checkin/redaction.py`, `directory/projection.py`, `assist/` (the one sanctioned egress point), `safety/` (deterministic alert origin), `bin/start.sh` + compose (protected files — same-message owner approval required), anything under `migrations/`. **These same modules carry the ≥95% branch-coverage floor and the mutation-testing scope (QUALITY_GATES §5.1, §8)** — the list is the authority for both, so extending one extends the other.
- **Never:** write AI output into a clinical table; bypass the tenancy/plane resolver; create a second egress point for a provider; add a clinical column to the platform store; commit without an explicit instruction; run destructive DB operations without same-message approval.
- **Model-tier hints:** **strong** for M1-T5/T6 (isolation + control plane), M4-T3/T4 (resolver/revocation), M5-T3/T7/T8 (redaction, job transport, adapter), M8-T2/T9/T11 (gating predicate, rule engine, prescribing gate); **standard** for the remaining context work; **light** for docs, locale files, seed scripts and test scaffolding.
- **Per-task contract:** restate the applicable R-rules, list the files, run the milestone's validation commands, attach the MOD-06 output for code (recording the **SPEC revision and the model version** that produced the slice), and report failures verbatim.
- **Sequencing rule:** never start a task whose SPEC is not Approved; never enable a job type whose evaluation bar has not passed.
- **Model-drift rule (R34):** the SPEC is the source of truth and generated code is **compiled output**. When a model update or tool change produces divergent output for the same SPEC, the fix is to **recompile/regenerate the affected slice from the SPEC** — never to hand-patch the generated code and let it drift from the intent. Version pins make each merged slice reproducible and diffable against its known-good baseline.

## 25. Long-Term Maintainability Strategy

- **Ownership:** one developer (owner) for now; every context has a named package and a service interface, so a second developer can be added per-context without archaeology.
- **Documentation upkeep:** ADRs are the decision record (never edited once Decided — superseded or amended by a new file); SPECs are amended, never rewritten; the registries are append-only histories.
- **Deprecation policy:** a superseded ADR keeps its file and gets a `Superseded by` status; a superseded SPEC keeps its file; the foundation docs are versioned by date prefix.
- **Review cadence:** architecture fitness review at each phase gate and before each staged milestone; the threat model is re-reviewed whenever a data flow changes; the observability spec is re-reviewed when a metric never triggers an action (deleted, not kept).
- **Model drift (R34 — the single biggest unique risk of AI-assisted development):** the SPEC is the source of truth; generated code is compiled output; divergent output from a model/tool change is fixed by recompiling the affected slice from the SPEC, never by hand-patching drift. Every merged slice records the **model version + SPEC revision** that produced it (MOD-06), so any divergence is reproducible and diffable against a known-good baseline.
- **Test debt (R35 — tests are the executable contracts):** a **test-health review** joins the quarterly cadence: flake rate, coverage drift on critical paths, and a **"test that never fails" sweep** (a test that has passed without ever being red is redundant or too weak). **The sweep is automated** from M8 by mutation testing on the dangerous paths (QUALITY_GATES §8) rather than performed by eye; CI (M12-T2) carries the flake policy.
- **Quarterly (or per-milestone):** the U19 cache review, the alert-quality review (false-positive rate), the dependency/security review, and the **test-health review** (R35).
