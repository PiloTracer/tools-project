1. Visual workflow automation engine

Functional requirements

Drag-and-drop graph editor; event and scheduled triggers; nested AND/OR conditions; sequential and parallel branches; approvals, delays, escalation, templates, simulation, execution history and immutable published versions.

Data model

workflow_definitions(id, tenant_id, name, status); workflow_versions(workflow_id, version, definition_json); workflow_instances(version_id, entity_id, status, context); workflow_step_runs(instance_id, node_id, input, output, attempts); workflow_approvals(instance_id, approver_id, decision, deadline); workflow_triggers(workflow_id, event_type, filter_json).

Backend and frontend implementation

Business transaction → transactional outbox → event dispatcher → trigger matcher → durable queue → execution workers → action registry. Use Temporal, Camunda or durable queue workers. Register typed action handlers; validate graph reachability, branching and cycles; persist checkpoints, retries, dead-letter queues and idempotency keys. Never evaluate arbitrary user code.

API contracts

POST /api/workflows; POST /api/workflows/{id}/validate; /publish; /simulate; GET /api/workflows/{id}/executions; POST /api/workflow-executions/{id}/retry; POST /api/approvals/{id}/decision

Example workflow

Opportunity won → evaluate contract value → if above $10,000 request manager approval; otherwise auto-approve → create project from onboarding template → assign team and notify.

Example structured configuration

{
  "version": 1,
  "trigger": {
    "event": "opportunity.won"
  },
  "nodes": [
    {
      "id": "check_value",
      "type": "condition",
      "expression": {
        "field": "opportunity.amount",
        "operator": "gt",
        "value": 10000
      }
    },
    {
      "id": "approval",
      "type": "request_approval",
      "role": "sales_manager"
    },
    {
      "id": "create_project",
      "type": "create_entity",
      "entity": "project",
      "template": "customer_onboarding"
    }
  ],
  "edges": [
    {
      "from": "check_value",
      "to": "approval",
      "branch": true
    },
    {
      "from": "check_value",
      "to": "create_project",
      "branch": false
    },
    {
      "from": "approval",
      "to": "create_project",
      "branch": "approved"
    }
  ]
}

Acceptance criteria

An administrator can automate onboarding without deployment; worker restart does not lose progress or duplicate actions.

Reference products

n8n; Salesforce Flow Builder; Monday.com automations

2. Custom fields, entities and dynamic forms

Functional requirements

Text, rich text, number, currency, percentage, dates, duration, dropdown, multi-select, user/entity references, attachments, formulas, conditional visibility, validation, relationships and custom layouts. Create equipment, contracts or inspections without per-entity migrations.

Data model

entity_definitions; field_definitions; entity_records; entity_relationships; form_definitions; view_definitions; configuration_versions. Use relational core fields and JSONB attributes with tenant/entity composite index, GIN index and targeted expression indexes.

Backend and frontend implementation

Use a field component registry (TextField, CurrencyField, DateField, SelectField, EntityLookupField, CalculatedField, AttachmentField). JSON Schema for validation and separate UI schema for layouts. Validate on server and client; typed formula evaluator with cycle detection; version and export configuration packages.

API contracts

GET /api/entity-definitions/{id}; POST /api/entities/{type}/records; PUT /api/forms/{id}; POST /api/configurations/export

Example workflow

Field metadata → schema validation → dynamic renderer → record persistence → search/report integration.

Example structured configuration

{
  "key": "contract_expiration",
  "label": "Contract expiration",
  "type": "date",
  "required": true,
  "searchable": true,
  "reportable": true,
  "validation": {
    "minField": "contract_start"
  },
  "visibility": {
    "field": "contract_type",
    "operator": "equals",
    "value": "fixed_term"
  }
}

Acceptance criteria

Admin creates an entity, form, relationships and permissions and uses it in reports without source changes.

Reference products

Odoo Studio; Salesforce custom objects; ClickUp custom fields

3. Unified Customer 360° workspace

Functional requirements

Consolidate contacts, opportunities, projects, tasks, contracts, invoices, tickets, communications, documents, customer health, commitments and outstanding payments.

Data model

accounts; contacts; account_relationships; opportunities; entity_links; activity_events; customer_health_snapshots.

Backend and frontend implementation

Build a customer read model using event-driven projections, cached aggregates or materialized views. Original modules remain authoritative. Configurable health score uses payment history, delays, tickets, communication and renewal risk; explain factors.

API contracts

GET /api/accounts/{id}/overview; /timeline; /relationships; /health; /financial-summary

Example workflow

Customer → activity timeline | projects | deals | finance → contextual actions.

Example structured configuration

{
  "event_type": "invoice.paid",
  "tenant_id": "tenant-001",
  "account_id": "account-123",
  "entity_type": "invoice",
  "entity_id": "invoice-456",
  "metadata": {
    "amount": 4500,
    "currency": "USD"
  }
}

Acceptance criteria

Customer-facing employee sees commercial, operational and financial situation from one permission-filtered workspace.

Reference products

HubSpot CRM; Salesforce Customer 360; Zoho CRM

4. Multi-view project and task management

Functional requirements

List, Kanban, Gantt, calendar, timeline, workload, spreadsheet table, portfolio and My Work; templates, recurring tasks, milestones, bulk editing, custom statuses, baselines, risk registers and rollups.

Data model

projects; project_sections; tasks; subtasks; task_assignees; task_dependencies(predecessor_id, successor_id, dependency_type, lag_minutes); task_comments; task_attachments; task_checklists; task_time_entries; saved_views.

Backend and frontend implementation

All views use the same task records. Support finish-to-start, start-to-start, finish-to-finish and start-to-finish. Detect cycles; topological sort; critical path; earliest/latest dates; working calendars, holidays and constraints; recalculate downstream dates. Fractional ranking for Kanban; optimistic concurrency.

API contracts

GET /api/projects/{id}/tasks?view=kanban; PATCH /api/tasks/{id}; POST /api/tasks/{id}/dependencies; POST /api/projects/{id}/reschedule

Example workflow

Discovery → Architecture → Development → QA & testing → Deployment.

Example structured configuration

{
  "name": "Engineering sprint",
  "entity": "task",
  "view_type": "kanban",
  "group_by": "status",
  "filters": [
    {
      "field": "department",
      "operator": "equals",
      "value": "engineering"
    }
  ],
  "sort": [
    {
      "field": "priority",
      "direction": "desc"
    }
  ],
  "visible_fields": [
    "title",
    "assignees",
    "due_date",
    "priority"
  ]
}

Acceptance criteria

Kanban move updates all views; predecessor changes recalculate dependent dates consistently.

Reference products

ClickUp; Monday.com; Asana; OpenProject

5. Configurable dashboards and visual report builder

Functional requirements

Drag-and-drop widgets, KPI cards, charts, pivots, funnels, cross-module reporting, calculated metrics, date filters, drill-down, schedules, exports and sharing.

Data model

report_datasets; report_dimensions; report_measures; report_definitions; dashboards; dashboard_widgets; report_schedules; report_cache.

Backend and frontend implementation

Semantic reporting layer compiles allowlisted dimensions, measures, joins and operators into parameterized SQL. Enforce row/field permissions before aggregation. Use materialized views, analytical replica or ClickHouse if justified. ECharts, Plotly or Highcharts subject to licensing.

API contracts

POST /api/reports/query; POST /api/reports; GET /api/dashboards/{id}; POST /api/reports/{id}/schedules

Example workflow

Report designer → report definition → semantic model → validated compiler → permission enforcement → database/cache → visualization.

Manager builds revenue by customer, salesperson and project, filters, drills down and schedules delivery.

Monday.com dashboards; Salesforce reports; Odoo spreadsheets

6. Unified communications and collaboration

Functional requirements

Record-level conversations, threads, mentions, email sync, shared inboxes, internal notes, attachments, live notifications, activity feeds, templates and preferences.

Data model

conversation_threads; messages; message_recipients; message_mentions; message_attachments; message_reactions; notification_events; notification_deliveries; notification_preferences; external_mailboxes; external_message_mappings.

Backend and frontend implementation

WebSockets or SSE, durable delivery queue, object storage and OAuth 2.0. Provider adapters for Gmail, Microsoft Graph and SMTP; use message/thread IDs, sync cursors and deduplication. Resolve recipients and preferences; support digests, quiet hours, grouping and escalation. Internal notes must never leak to customers; attachments inherit parent permissions.

API contracts

POST /api/threads/{id}/messages; GET /api/notifications; PATCH /api/notification-preferences; POST /api/mailboxes/{id}/sync

Example workflow

Domain event → policy evaluator → recipient resolution → preference filter → delivery queue → in-app/email/push/webhook.

Example structured configuration

{
  "thread_id": "thread-123",
  "entity_type": "project",
  "entity_id": "project-456",
  "channel": "internal",
  "visibility": "team",
  "body": "Ready for QA",
  "mentions": [
    "user-321"
  ]
}

Acceptance criteria

Team discusses tasks, mentions colleagues, attaches files and reviews customer communications in one workspace.

Reference products

ClickUp comments; HubSpot inbox; Odoo chatter

7. Resource, workload, time and profitability management

Functional requirements

Availability, working calendars, leave, skills, planned allocations, time tracking, timesheet approvals, billable hours, cost/billing rates, budgets and forecasts.

Data model

resource_profiles; resource_skills; work_calendars; resource_allocations; time_entries; timesheets; resource_rates; project_budgets; project_cost_entries.

Backend and frontend implementation

Utilization = allocated / available hours × 100; labor cost = sum(actual hours × effective cost rate); gross margin = (revenue − direct costs) / revenue × 100. Handle zero denominators, currency conversion, historical rates, overlapping entries, time zones and partial working days. Store money as decimal with currency code.

API contracts

GET /api/resources/workload; POST /api/time-entries; POST /api/timesheets/{id}/approve; GET /api/projects/{id}/profitability

Example workflow

Capacity calendar → allocations → actual time → effective rates → budget variance → profitability.

Example structured configuration

{
  "contract_revenue": 25000,
  "labor_hours": 320,
  "hourly_cost": 45,
  "other_direct_costs": 2000,
  "gross_profit": 8600,
  "gross_margin_percent": 34.4
}

Acceptance criteria

Manager identifies overloaded staff, forecasts staffing and detects budget/profitability risk.

Reference products

Float; ClickUp workload; Productive

8. Advanced permissions, security and audit trails

Functional requirements

RBAC, ABAC, relationship-based access, row and field security, tenant isolation, MFA, SSO via OIDC/SAML, session revocation and scoped service accounts.

Data model

roles; permissions; role_permissions; user_roles; teams; team_members; access_policies; record_access_grants; field_permissions; audit_events.

Backend and frontend implementation

Central default-deny backend policy enforcement; database row-level security as defense in depth. Apply to search, reports, exports, jobs and attachments. Append-only audit with actor, tenant, entity, action, old/new values, correlation ID and timestamp. Redact secrets; restrict audit access; immutable storage for higher assurance. Consider OPA, Casbin, OpenFGA.

API contracts

GET /api/permissions/effective; POST /api/access-policies; GET /api/audit-events

Example workflow

Request → authenticate → tenant scope → role/relationship/attribute policy → field filtering → audit.

Example structured configuration

{
  "effect": "allow",
  "resource": "project",
  "actions": [
    "read",
    "update"
  ],
  "conditions": {
    "all": [
      {
        "left": "resource.tenant_id",
        "operator": "equals",
        "right": "subject.tenant_id"
      },
      {
        "left": "resource.members",
        "operator": "contains",
        "right": "subject.id"
      }
    ]
  }
}

Acceptance criteria

Unauthorized records cannot be accessed through direct IDs, APIs, exports, search, attachments or jobs.

Reference products

Odoo access groups; Salesforce permission sets

9. Global search and command palette

Functional requirements

Cross-module fuzzy search, typo tolerance, autocomplete, recent records, saved searches, keyboard navigation, document indexing and commands to create records, start timers, assign tasks or change status.

Data model

search documents: id, tenant_id, entity_type, entity_id, title, description, keywords, updated_at; search_history; saved_searches; command_registry.

Backend and frontend implementation

Transactional outbox → indexing worker → search engine → permission-aware API. PostgreSQL full-text search and pg_trgm initially; OpenSearch, Elasticsearch, Typesense or Meilisearch at scale. Rank exact/title matches, relevance and recency. Revalidate authoritative permissions before returning snippets or counts.

API contracts

GET /api/search?q=payment; GET /api/search/suggestions?q=pay; GET /api/search/recent; GET /api/commands; POST /api/commands/{id}/execute

Example workflow

Ctrl+K → search records or actions → permission check → navigate or execute.

Example structured configuration

{
  "id": "task:123",
  "tenant_id": "tenant-456",
  "entity_type": "task",
  "entity_id": "123",
  "title": "Implement payment gateway",
  "keywords": [
    "payments",
    "integration",
    "backend"
  ]
}

Acceptance criteria

Find any authorized record from anywhere; target sub-300 ms search under normal load.

Reference products

Linear; Notion; Raycast

10. Integration engine and extensibility framework

Functional requirements

Public APIs, incoming/outgoing webhooks, OAuth, connectors, scheduled sync, field mapping, transformations, imports/exports, custom modules and monitoring.

Data model

integration_definitions; integration_connections; integration_field_mappings; integration_sync_states; external_record_mappings; integration_jobs; webhook_subscriptions; webhook_deliveries; extension_manifests.

Backend and frontend implementation

Connector contract: authenticate, testConnection, discoverSchema, fetchChanges(cursor), pushChanges(records), handleWebhook(request). Signed webhooks, idempotency, backoff, dead-letter queues, checkpoints, conflict resolution, secret rotation and tenant rate limits. Define field ownership; isolate extensions and declare scopes; never load arbitrary third-party code into core process.

API contracts

POST /api/integrations/connections; POST /api/integrations/{id}/sync; POST /api/webhooks/subscriptions; GET /api/integration-jobs

Example workflow

Email/calendar/accounting/payments → integration gateway → mapping/validation → event bus → CRM/projects/ERP/extensions.

Example structured configuration

      "contracts.generate"

New integration uses standard connector contract without modifying core.

Zapier; Make; Odoo Apps

Shared architecture and implementation roadmap

Share metadata, workflows, authorization, events, reporting, search, notifications and integration gateway. Prefer a modular monolith initially. Standardize entity IDs, tenant IDs, entity types, timestamps, actor IDs, row versions and custom fields. Standardize filtering, sorting, export, authorization, activity, attachments and workflow participation.

Use a transactional outbox. One opportunity.won event can create a project, update dashboards and timeline, notify employees, index search and synchronize integrations.

Dependency-based roadmap

  1. Authorization, audit, events and metadata foundations.
  2. Custom fields, Customer 360°, project views and search.
  3. Workflow automation and collaboration.
  4. Reporting, resource planning and profitability.
  5. Integration and extension framework.

Mandatory engineering requirements

Backward-compatible migrations; OpenAPI and consistent errors; tenant isolation; pagination, indexing, caching and query budgets; idempotency and retries; optimistic locking; structured logs, metrics and tracing; unit, integration, end-to-end and authorization tests; feature flags; WCAG 2.2 AA target; localization, currencies and time zones; import/export; preserve existing records, APIs and workflows.

Instructions for AI coding agents

Act as principal software architect and senior full-stack engineer. Inspect repository, architecture, schema, API conventions, frontend, authentication, authorization, jobs and deployment before coding. Identify existing, partial and missing capabilities. Produce gap analysis, dependency graph, reusable services, adapted data models and API contracts, migration risks and incremental plan. For each feature deliver design, migrations/indexes, domain services, APIs/OpenAPI, frontend workflows, permissions, events, loading/empty/error/success states, tests, performance, deployment/rollback and user/admin documentation. Preserve existing functionality; avoid destructive migrations, framework changes and duplicate infrastructure. Use metadata-driven reusable services and feature flags. Verify persistence, authorization, validation, concurrency, recovery and tests, not just UI. Document limitations after each phase.
