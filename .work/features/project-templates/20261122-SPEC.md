# Project templates — Feature SPEC

**Status:** Approved
**Needs:** Implementation. No further product decision.
**Owner:** Engineering
**ADRs referenced:** none — additive catalog; no new service
**Related plans:** work-type colors stay as shipped (`web/src/components/WorkTypeBadge.tsx`, `seed_work_types_for_project`); prospect onboarding stays on its own task list (`.work/features/opp-to-project-auto/20260629-SPEC.md`)
**Slug:** project-templates

A template is a ready-made way of working, in the sense of the Jira template gallery (https://www.atlassian.com/software/jira/templates). Creating a project from one copies that process onto the new project: board columns, item types, and a few starter items. **Basic** leaves today's project unchanged. Existing projects are not rewritten.

## 1. Purpose

The gallery at that link is a catalog of processes, tagged by team. Recruitment tracks a candidate from application to offer on a board whose columns are that pipeline. Bug tracking captures an issue and moves it through its own steps. Sales pipeline, month-end close, campaign, procurement, and the others are the same kind of object.

This product already has one task board for every project: Todo, In Progress, Blocked, Done, Cancelled (`web/src/components/KanbanBoard.tsx`). Work types are a color and a name on an item. They stay. This SPEC adds a choice at project creation. The chosen process becomes that new project's columns, its item types (stored as work types, so the existing marks keep working), and its first items. A superuser can add another process later, under any team name, without a schema change.

The first deliverable ships Basic plus one real process for each team named below. Calendar, forms, and reports from the Jira pages are later work. This app does not have those views.

## 2. In scope / Out of scope

### In scope
- Template catalog grouped by team: Basic, plus one process each for Engineering, HR, Design, Legal, Finance, IT, Project Management, Sales, Marketing, and Operations.
- Each process template copies, onto the new project only:
  - board columns (key, label, order, which columns are finished),
  - item types as work types (one default),
  - starter tasks, each placed in a column and given an item type.
- **Basic** runs today's `seed_work_types_for_project`, inserts no column rows, and inserts no starter tasks. The task board keeps the five columns it has today.
- A project with column rows shows those columns on the task board, the task detail status control, and the task list filter. Task status must be one of those column keys.
- A project with no column rows keeps today's task statuses and today's ticket statuses.
- `POST /v1/projects` accepts optional `template_key`. Omitted means `basic`.
- A superuser can add a template: team name, process name, columns, item types, starter items.
- Startup inserts a shipped template only when its key is absent. It does not update or delete stored template rows, and it does not touch projects, tasks, tickets, or work types.
- `projects.template_key` nullable, no foreign key, no backfill. Existing rows stay null.

### Out of scope
- Rewriting any existing project, task, ticket, work type, or member.
- Changing a project's template after creation, or re-applying a template.
- Ticket columns. Tickets stay on Open, In Progress, Waiting, Resolved, Closed for every project.
- Timeline, calendar, forms, and reports.
- Per-template custom fields.
- Editing or deleting a shipped template in the UI.
- Plan import into a process-template project. Plan import keeps creating and updating tasks on projects that use the global statuses. Calling it for a project that has its own columns returns `409` and writes nothing.
- Prospect promotion. It still creates a project with a null `template_key`, the current work-type seed, and its seven onboarding tasks.

## 3. Domain language

| Term | Meaning |
|------|---------|
| Template | A named process: team, description, columns, item types, starter items. |
| Basic | Key `basic`. Today's new project. No column rows. |
| Team | The gallery group: Engineering, HR, and the other names in §4. Stored as text, not an enum. |
| Column | One step on that project's task board. The task's `status` is the column key. |
| Finished column | A column that closes the task (`closed_at` set), the way Done and Cancelled do today. |
| Item type | A work type copied onto the project. Color and shape come from the existing badge. |
| Snapshot key | `projects.template_key`. Records the choice. Later edits to the template do not flow into the project. |
| Global statuses | `todo`, `in_progress`, `blocked`, `done`, `cancelled` for tasks when the project has no column rows. |

## 4. Behavioural spec

### Apply

- **R1.** `POST /v1/projects` with no `template_key` behaves as `basic`.
- **R2.** `basic` sets `template_key` to `basic`, runs `seed_work_types_for_project` for that new project only, and inserts no `project_board_columns` and no starter tasks.
- **R3.** Any other known key sets `template_key`, does not run the general work-type seed, and copies that template's columns, work types, and starter tasks onto that new project only.
- **R4.** Unknown or blank `template_key` returns `400` and creates no project.
- **R5.** The copy and the project insert commit together. A failure leaves no project, no columns, no work types, and no tasks.
- **R6.** Each starter task is `priority = normal`, unassigned, reported by the creator, `status` equal to its column key, and `work_type_id` equal to its item type. A finished column sets `closed_at`.
- **R7.** Prospect promotion does not set `template_key`. Its seed and `ONBOARDING_TASKS` stay as they are.
- **R8.** Existing projects are not updated. A null `template_key` stays null. Their task statuses stay the values already stored.

### Board and status

- **R9.** When a project has `project_board_columns` rows, the task board, task detail status control, and task status filter use those rows in `sort_order`. The hardcoded five task columns are not shown.
- **R10.** When a project has no column rows, the task board and status checks stay on the global statuses. Ticket columns stay on the global ticket statuses for every project.
- **R11.** Creating or updating a task status on a project with column rows accepts only those column keys. Any other string, including a global status that is not one of the columns, returns `400`.
- **R12.** Creating or updating a task status on a project with no column rows accepts only the global statuses, as today.
- **R13.** Moving a task onto a finished column sets `closed_at`. Moving it onto a column that is not finished clears `closed_at`.
- **R14.** Plan import against a project that has column rows returns `409` and does not write tasks.

### Catalog

- **R15.** `GET /v1/project-templates` returns every template. Basic first, then team name, then template name. Any signed-in user who can create a project may read it.
- **R16.** `POST /v1/project-templates` is superuser-only. Body: `team` (text, required for a custom template), `name`, optional `description`, `columns[]` (label, `is_finished`, at least one column, exactly the order given), `work_types[]` (name, optional description, exactly one default), `items[]` (title, column label, work-type name). The server derives keys with the work-type slug rules, max 32.
- **R17.** A duplicate template key returns `409`. A body with no columns, no work types, a default count other than one, or a starter item whose column or type is not in the body returns `400`.
- **R18.** Shipped templates cannot be deleted through the API. Deleting a custom template removes the catalog rows only. Projects that already copied it keep their columns, work types, tasks, and snapshot key.

### Startup

- **R19.** On every API start, each shipped key in §4 is inserted if absent. A key that already exists is not updated and not deleted, including its columns, types, and items.
- **R20.** A second start inserts nothing when those keys are present.
- **R21.** Startup does not `UPDATE` or `DELETE` `projects`, `tasks`, `tickets`, `work_types`, `work_type_starter_grants`, or `project_board_columns`.

### Shipped processes

Basic has no column, type, or item rows. Its apply path is R2.

Column lists are in order. A column marked finished is the only kind that sets `closed_at`. The first item type is the default. Starter items are `title → column`.

| Team | Key | Name | Columns | Item types | Starter items |

Work-type keys are the slug of the name (`close-task`, `deal`). Descriptions are one sentence in the seed. Reserved badge hues stay. Any other key uses the badge's existing diamond and stable hue. This deliverable does not edit `WorkTypeBadge`.

## 5. Data model

`project_templates` — `id`, `key VARCHAR(32)` unique, `name VARCHAR(200)`, `team VARCHAR(80)` null for Basic, `description` text null, `is_builtin` boolean, timestamps.

`project_template_columns` — `template_id` FK cascade, `key VARCHAR(32)`, `label VARCHAR(80)`, `sort_order` int, `is_finished` boolean. Unique `(template_id, key)`.

`project_template_work_types` — `template_id` FK cascade, `key`, `name`, `description` null, `is_default`, `sort_order`. Unique `(template_id, key)`. One default per template.

`project_template_items` — `template_id` FK cascade, `title VARCHAR(200)`, `column_key`, `work_type_key`, `sort_order`.

`project_board_columns` — `project_id` FK cascade, `key VARCHAR(32)`, `label VARCHAR(80)`, `sort_order` int, `is_finished` boolean. Unique `(project_id, key)`. Copied at apply. No rows means "use the global task statuses."

`projects.template_key VARCHAR(32)` null. `ADD COLUMN IF NOT EXISTS`. No foreign key. No backfill.

All new tables use `CREATE TABLE IF NOT EXISTS`. Seed goes in `sql/schema_inserts.sql`: insert the template when its key is absent, then insert children only when that template has zero column rows. Basic is a catalog row so the gallery can list it, and it has zero children.

`tr_projects_seed_work_types` still calls `seed_work_types_for_project` when `template_key` is null or `basic`. Any other non-null key returns without seeding. The application copies the process in that same transaction.

Task `status` stays `VARCHAR(40)`. No change to existing status values.

| Method | Path | Who | Result |
|--------|------|-----|--------|
| GET | `/v1/project-templates` | signed-in user | items with `team`, `columns`, `work_types`, `items` |
| POST | `/v1/project-templates` | superuser | `201` |
| DELETE | `/v1/project-templates/{id}` | superuser | `204` custom, `409` shipped |
| POST | `/v1/projects` | creator | existing body plus optional `template_key` |
| GET | `/v1/projects/{id}/board-columns` | project member | the copied columns, or an empty list when the project uses the global statuses |

Task create and patch use R11 and R12. Web BFF mirrors the new routes. No agent-API change.

## 7. Invariants

- **I1.** Startup SQL for this feature contains no `UPDATE` or `DELETE` against `projects`, `tasks`, `tickets`, `work_types`, `work_type_starter_grants`, or `project_board_columns`.
- **I2.** Apply writes rows only for the project id created in that transaction.
- **I3.** A project with no `project_board_columns` still accepts the five global task statuses and rejects nothing it accepts today.
- **I4.** Re-running startup with the shipped keys present leaves template row counts unchanged.
- **I5.** Exactly one default work type on every non-basic template and on every project that template creates.
- **I6.** A restored database keeps its projects, tasks, and tickets. Startup adds only missing template keys and missing tables or the new column.

## 8. Error model

| Case | HTTP | Detail |
|------|------|--------|
| Unknown `template_key` | 400 | `unknown_template` |
| Invalid template body | 400 | `invalid_template` |
| Duplicate template key | 409 | `template_key_taken` |
| Non-superuser writes the catalog | 403 | existing forbidden detail |
| Delete of a shipped template | 409 | `builtin_template` |
| Missing template id | 404 | `template_not_found` |
| Task status not in the project's columns, or not in the global set when it has none | 400 | `invalid_status` |
| Plan import on a project that has columns | 409 | `template_project` |

The create transaction rolls back. No partial project is returned.

## 9. Observability

One log line `project.template_applied` with `template_key` and `project_id`. One line `project.template_created` with the new key. No titles, descriptions, or email addresses.

## 10. Security and privacy

Catalog reads follow project-creation permission. Catalog writes are superuser-only. Column keys and template keys are slugs. Starter titles are plain text on the existing task title path. Sample titles in §4 are role and process words, not people's names.

## 11. Test plan

1. Create with no `template_key` → `basic`, work types match a direct seed call, zero `project_board_columns`, zero tasks. The board column endpoint returns an empty list.
2. Create with `bug-tracking` → columns match §4 in order, work types are Bug, Improvement, and Investigation, three tasks sit on Captured, Triaged, and In progress, and the general seed did not also run.
3. Create with `recruitment` → a task can move to Hired and then has `closed_at` set; moving it back to Interview clears `closed_at`; status `todo` returns `400`.
4. Create with `nope` → `400`, project count unchanged.
5. A project created before this column, with a task in `in_progress`, still patches to `done` after startup. Its task count and work-type count are unchanged. Its column endpoint is empty.
6. Startup twice → shipped template count unchanged. An edited Bug tracking description survives the second insert.
7. Superuser adds team "Facilities" with two columns, two types, and one item. A member receives `403`. Creating from that key copies them. Deleting the shipped Bug tracking template returns `409`. Deleting Facilities returns `204`, and the project already created from it still has its columns and task.
8. Prospect promotion still creates seven tasks, null `template_key`, and no column rows.
9. Plan import on a `basic` project still works. Plan import on a `bug-tracking` project returns `409` and adds no task.
10. SQL runner twice on a database that already has a project, a task, and a ticket: those three row counts stay the same, and `projects.template_key` exists.

## 12. Rollout and rollback

**Rollout.** SQL and app ship together. API start already runs `schema_changes.sql`, `schema_indexes.sql`, bootstrap, `schema_backfill.sql`, `schema_inserts.sql`. No manual SQL. No backfill of old projects.

**Rollback.** Revert the app and leave the new tables and the nullable column. Old code ignores `template_key` and `project_board_columns`. The trigger branch ships in the same release as the copy, so a non-basic key cannot skip the seed without the copy. Do not drop tables on rollback.

**Rebuild.** An empty database gets the tables and the shipped catalog. A restored database keeps its rows. Startup fills only missing catalog keys and missing structure.
