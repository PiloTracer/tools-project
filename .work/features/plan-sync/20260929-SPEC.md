## 1. Purpose

Sync-from-plans: import Agent OS plan markdown (`.work/feedback/plans-import/`) into the project system as a first-class, progressive structure — projects carry **ordered milestones**, milestones carry **tasks with definitions of done**, and re-running a sync after a plan revision reconciles the work (including marking tasks the new plan makes obsolete) without duplicating, deleting, or regressing anything.

---

## 2. In scope / Out of scope

### In scope
- New `milestones` table + `tasks.milestone_id` / `tasks.plan_ref` / `tasks.plan_state` columns (DDL in `sql/`, restart-run, idempotent)
- Milestone CRUD API (list ordered, create, patch/transition)
- Transactional bulk import endpoint `POST /v1/projects/{id}/plan-import` with `dry_run`
- Re-sync semantics: upsert by `plan_ref`, local-status-wins, obsolete matrix, reactivation, conflict report
- Side-effect suppression during import (one summary activity; single deferred GitHub registry push)
- `auto_prefix_enabled` decoupled from GitHub link/token check (D6)
- `X-Api-Key` accepted on the import endpoint only (D7)
- Task list filters `milestone_id`, `plan_state`; milestone progress roll-up
- Web UI: milestone list, milestone filter/column, milestone chips, obsolete badge/filter
- Agent skill `@plan-sync` (framework side): plan → validated manifest → preview → POST → report
- Backend tests for the import matrix + migration idempotency

### Out of scope
- Import of risks / unknowns / assumptions / decision logs / FR-NFR tables / traceability matrices
- Any write-back into `.work/` (`NEXT.md`, `HANDOFF.md`) — sync is one-way (plan → app)
- Generic bulk-create API for arbitrary payloads
- Kanban columns grouped by milestone, timeline/gantt, inter-milestone dependencies, burndown
- `stages` / `iterations` tables; nested milestones (`parent_milestone_id`)
- Deleting tasks or milestones on re-sync
- New migration files or ORM migration tooling (DDL goes only into the existing restart-run `schema_*.sql`)
- BC1…BC14 → `components` mapping (deferred, P4 polish)

## 3. Domain language

| Term | Definition |
|------|------------|
| Milestone | First-class ordered unit of sequence within a project (`M1…M12`); carries status, gate/acceptance text and progress |
| Iteration / stage | **Same entity as milestone** — the iteration is the milestone whose status is `active` (D2) |
| Plan reference (`plan_ref`) | Stable plan-native ID (`M4-T4` for tasks, `M4` for milestones); unique per project; re-sync match key |
| Plan state (`plan_state`) | Provenance of an item vs the current plan: `active` (plan still calls for it) or `obsolete` (a plan revision dropped it) |
| Manifest | Versioned JSON envelope produced by the `@plan-sync` agent skill and consumed by the import endpoint |
| Obsolete | Work dropped by a plan revision; flagged via `plan_state`, never deleted |
| Conflict | An import finding that requires human resolution (notably an in-progress task absent from the new plan) |

## 4. Behavioural spec

### Milestone structure

- **R1** A project may contain zero or more milestones. Milestones are ordered by `sort_order` (integer, ascending); `key` (e.g. `M1`) is an optional human label and is **not** the sort key (text sort would order `M1, M10, M11, M2`).
- **R2** Milestone status vocabulary: `pending | active | blocked | done | cancelled` (default `pending`). At most one milestone per project may be `active` at a time — that milestone **is** the current iteration; transitioning one to `active` clears `active` on any other milestone of the same project (single-writer transition inside one transaction).
- **R3** `GET /v1/projects/{id}/milestones` returns milestones ordered by `sort_order`, each with task totals (`total`, `done`) sufficient to render a progress bar server-side.
- **R4** Tasks reference a milestone via nullable `milestone_id` (`ON DELETE SET NULL`); `parent_task_id` remains reserved for genuine one-level sub-task breakdown and is never used to model milestones.

### Import pipeline

- **R5** `POST /v1/projects/{id}/plan-import` accepts a manifest with `manifest_version` (only `1` accepted initially), `source_path`, `plan_version`, `project`, `milestones[]`, `tasks[]`, optional `components[]`. Unknown `manifest_version` → 400, nothing written.
- **R6** Manifest validation (400 with a per-field error list, nothing written): every task has `plan_ref` matching `M{N}-T{N}` and a `title` of 1–200 chars; every milestone has `plan_ref` matching `M{N}` and a `name`; `plan_ref` values are unique within the manifest; every task's `milestone_ref` exists in `milestones[]`; `tasks[]` ≤ 500 and `milestones[]` ≤ 100 per import.
- **R7** `dry_run: true` performs full validation and returns the diff report **without writing**. The agent skill always runs `dry_run` before commit; the preview is what the operator approves.
- **R8** Commit applies everything in **one database transaction** — a failure at any point leaves the project exactly as before (no partial imports).
- **R9** Import side effects are suppressed per row: exactly **one** summary activity row per import (`kind: system`, body summarising created/updated/obsolete counts); task `ref` allocation + counter increment still occur per task; **at most one** GitHub task-registry push after commit (not one per task).
- **R10** Import performs **no** webhook dispatches (`task.done` etc.) even when creating tasks already in `done` status.
- **R11** Import requires project write permission (`can_create_tasks` for contributor+ scope). Authentication accepts either Bearer JWT **or** `X-Api-Key` header (D7) — the only mutating endpoint that accepts `X-Api-Key`. All other write endpoints remain JWT-only.

### Re-sync semantics

- **R12** Items are matched across runs **only** by `(project_id, plan_ref)` — enforced by partial unique indexes. IDs are never reused across projects.
- **R13** On match (existing item in manifest): refresh content fields (`name`/`title`, `description`, `summary`, `sort_order`, `milestone_id`, milestone `key`/`due_at`/`start_at`); **preserve local `status` unconditionally** — a plan revision can never revert `done` → `todo` or kill an `in_progress` state by itself. Manifest-vs-local status divergence is reported, not applied.
- **R14** New item in manifest → create (status from plan mapping: `pending→todo`, `done→done`, `blocked→blocked`, `deferred→cancelled`; `plan_state='active'`).
- **R15** **Obsolete matrix** — item exists locally with `plan_state='active'` but is absent from the manifest:

| Local `status` | Action |
|----------------|--------|
| `todo` / `blocked` | → `status='cancelled'`, `plan_state='obsolete'`, `closed_at` set per terminal rules |
| `in_progress` | **No change** — reported as `conflict`; never auto-killed |
| `done` | `status` unchanged; `plan_state='obsolete'` |
| `cancelled` | `plan_state='obsolete'` only |

- **R16** Milestones absent from the manifest follow R15 with the milestone vocabulary (`done` keeps `done`; otherwise → `cancelled`), and are flagged via `plan_state`.
- **R17** **Reactivation:** an item with `plan_state='obsolete'` present again in a later manifest → `plan_state='active'`; if sync had set `status='cancelled'`, restore `status='todo'`. Human-set `cancelled` on an `active` item is never touched by sync.
- **R18** **Nothing is ever deleted** by sync. Obsolete items remain stored and are retrievable via `plan_state=obsolete` filter (auditable history).
- **R19** The diff result returned by every commit run: `{created, updated, obsolete, reactivated, conflicts[]}` with counts per entity type (milestones/tasks) and a human-readable conflict list (reason per entry).
- **R20** Conflicts reported (and not auto-applied): R15 in-progress orphans; title >200 in manifest (rejected at R6); duplicate `plan_ref` (rejected at R6); task referencing a milestone not in the manifest (rejected at R6); `sort_order` collisions within a project (warning, last-write wins).

### Task content mapping

- **R21** Task `title` = manifest `title` (agent-authored, ≤200). Full plan cell content goes to `description` with this order: `## Acceptance` block first (the contract), then `## Source` provenance block (`plan_ref`, source file, plan version, complexity, FR/NFR traces, files).

> **Amendment R21a (2026-09-30, owner request — readability of imported tasks).** The
> description is composed as **three stable blocks**: `## Intent` (one plain-language sentence:
> what the task delivers), `## Acceptance` (one bullet per criterion), `## Technical details`
> (a `- key: value` list: `plan_ref`, `plan_version`, `source`, `files`, `traces`, `complexity`).
> The `---` rule and the inline `**Provenance:** …` line are retired; `## Source` folds into
> `## Technical details`. The task `title` is the **short human label** (≤ 120 chars, first
> clause of the plan cell, no markdown emphasis); the rest of the cell moves into `## Intent` /
> `## Technical details`, and milestone `summary` carries one plain sentence. Technical values
> stay verbatim (no truncation, no re-wording) and the manifest envelope is unchanged.
> **Readers must tolerate both shapes**: R21 (as originally written), the drift actually shipped
> (`---` + `**Provenance:** plan_ref=…, files=…`), and R21a — the web parser
> (`web/src/shared/plan-text.ts`) accepts all three, and imports that *match* an existing
> `(project_id, plan_ref)` refresh `title`/`description`/`summary`, so a re-sync upgrades
> previously imported tasks in place (R13 preserved: local `status` is never touched).
> Framework-side work order for the skill: `.work/feedback/adjustments-for-plan-sync-skill/`.
- **R22** Plan `Complexity` is **never** mapped to `priority`. Plan `FR/NFR` columns are carried as description text only.

### Settings decoupling

- **R23** `auto_prefix_enabled` may be enabled when `project_key` is set, **without** a linked GitHub repository or token validation (D6). `github_task_registry_enabled` continues to require a linked repo + live token check. Enabling prefix on a project with no GitHub link must not 400.
- **R24** With `auto_prefix_enabled=true`, imported tasks receive `ref` values from the existing counter — never `NULL`.

### Filters and UI

- **R25** `GET /v1/projects/{id}/tasks` supports `milestone_id` and `plan_state` query filters alongside the existing `component_id`.
- **R26** Web UI (v1): milestone list with progress bars on the project page; milestone filter + column on the Tasks table; `plan_state` filter (default `active`, `obsolete` opt-in); milestone chip row scoping the board; "Obsolete" badge on tasks/milestones with `plan_state='obsolete'`; task detail shows `milestone_id`, `plan_ref`, `plan_state`.

### Migrations

- **R27** All DDL lives in `sql/schema_changes.sql` + `sql/schema_indexes.sql`, executed automatically by the API lifespan on **every** container start (`SQL_SCHEMA_APPLY`, default true). Every statement is idempotent (`IF NOT EXISTS`, guarded `ADD COLUMN`) — a restart re-runs it with zero errors and no duplicate objects. No new migration files are added.

## 5. Data model

### New table `milestones`

| Column | Type | Constraints |
|--------|------|-------------|
| `id` | UUID | PK, default `gen_random_uuid()` |
| `project_id` | UUID | NOT NULL, FK → `projects(id)` ON DELETE CASCADE |
| `key` | VARCHAR(32) | nullable (e.g. `M1`); unique per project (partial) |
| `name` | VARCHAR(200) | NOT NULL |
| `summary` | TEXT | nullable |
| `description` | TEXT | nullable |
| `status` | VARCHAR(40) | NOT NULL DEFAULT `'pending'` |
| `plan_state` | VARCHAR(16) | NOT NULL DEFAULT `'active'` |
| `sort_order` | INT | NOT NULL DEFAULT 0 |
| `start_at` / `due_at` | TIMESTAMPTZ | nullable |
| `plan_ref` | VARCHAR(64) | nullable; unique per project (partial) |
| `created_by` | UUID | FK → `users(id)` ON DELETE SET NULL |
| `created_at` / `updated_at` | TIMESTAMPTZ | NOT NULL DEFAULT now() |

### `tasks` — new columns (all nullable/defaulted; existing rows untouched)

| Column | Type | Constraints |
|--------|------|-------------|
| `milestone_id` | UUID | nullable, FK → `milestones(id)` ON DELETE SET NULL |
| `plan_ref` | VARCHAR(64) | nullable; unique per project (partial) |
| `plan_state` | VARCHAR(16) | NOT NULL DEFAULT `'active'` |

### Indexes (partial uniques in `schema_indexes.sql`, not in ORM models — matches `commit_subject_ref` pattern)

- `uq_milestones_project_key (project_id, key) WHERE key IS NOT NULL`
- `uq_milestones_project_ref (project_id, plan_ref) WHERE plan_ref IS NOT NULL`
- `uq_tasks_project_plan_ref (project_id, plan_ref) WHERE plan_ref IS NOT NULL`
- `ix_milestones_project_status`, `ix_milestones_project_sort`, `ix_tasks_project_milestone`, `ix_tasks_project_plan_state`

## 7. Invariants

- **I1** Sync is one-way: plan → app. No code path writes to `.work/`.
- **I2** `(project_id, plan_ref)` is unique per table (DB-enforced).
- **I3** Local `status` is never changed by manifest content (only by the R15 obsolete matrix or R17 reactivation).
- **I4** Sync never deletes rows.
- **I5** An import is atomic: all-or-nothing.
- **I6** At most one `active` milestone per project at commit time.
- **I7** Import is the **only** bulk write path for tasks/milestones; single-row CRUD stays in the existing routers; both go through the same ORM models (no raw SQL from Python).
- **I8** Per-import side effects bounded: ≤1 activity row, ≤1 registry push regardless of item count.
- **I9** All DDL remains idempotent and restart-run (R27).
- **I10** `plan_state` is provenance only — it never affects permissions, ordering, or status transitions.

## 8. Error model

| Condition | HTTP | Detail |
|-----------|------|--------|
| Manifest fails schema (R6) | 400 | Field-level error list; nothing written |
| Unknown `manifest_version` | 400 | `Unsupported manifest_version: X` |
| Manifest size limits exceeded | 400 | `tasks ≤ 500, milestones ≤ 100` |
| No authentication | 401 | Existing shape |
| Insufficient project role | 403 | `Not permitted to import into this project` |
| Project not found | 404 | `Project not found` |
| `plan_ref` collision with **another project's** item | 409 | (should not occur — refs are project-scoped; guard) |
| Transaction failure | 500 | Rollback; project unchanged; error logged with `import.failed` |

## 9. Observability

- Log lines (structured): `plan_import.start` (project, counts), `plan_import.dry_run` (diff counts), `plan_import.complete` (created/updated/obsolete/reactivated/conflicts, duration), `plan_import.failed` (error, rollback).
- One summary `activities` row per successful commit import (R9) — visible in the project feed as the durable audit trail.
- Existing request middleware (X-Request-Id) applies; no new metrics required for v1.

## 10. Security and privacy

- Import endpoint: project RBAC (contributor+) enforced on top of auth; `X-Api-Key` acceptance limited to this route (D7) — shared agent key still rejected when multi-tenancy is enabled (existing rule in `require_agent_or_user`).
- D6 does not weaken GitHub gating: token validation remains mandatory for `github_task_registry_enabled`; only the independent prefix setting is decoupled.
- No new PII surfaces; manifests contain plan content only. Secrets never appear in manifests, logs (counts/ids only), or activities.
- Manifests are untrusted input: pydantic validation, size caps (R6), parameterized SQL only.

## 12. Rollout and rollback

- **Additive only.** New table + 3 nullable/defaulted columns; existing rows untouched; no feature flag needed. Existing projects behave identically until a sync is run.
- DDL applies automatically on API container start (R27) — deploy = ship code + restart (consistent with `0004-hosting-deployment.md`).
- **Rollback:** revert the code; new columns/table are inert (no reader, no writer). Dropping them is optional and never automatic — forward-fix preferred. `SQL_SCHEMA_APPLY=false` remains the operator kill-switch for DDL during a rollback window.
- Release notes: `.work/features/plan-sync/CHANGELOG.md` at deploy time (FEATURE_STANDARD §2 stage 4).
