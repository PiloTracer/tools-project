## 1. Purpose

Add **client companies** and **client contacts** as first-class entities, and allow projects to be scoped to a client with limited-access participation for external stakeholders. This bridges the gap between the current internal-only project management tool and a full agency workflow: clients engage us, we create projects for them, their team sees relevant progress, and our internal team manages the work.

---

## 2. Out of scope

- Full ERP (invoicing, billing, time tracking, resource scheduling)
- Public client portal / SSO (clients log into `/client/login` with limited scope)
- Automated email notifications (V2)
- Multi-tenant isolation (still single-org tool)
- GitHub-style commit visibility for clients
- Client-facing SLA or uptime dashboards
- Native mobile apps

---

## 3. Functional requirements

### FR-1: Client companies
The system shall allow creating, listing, viewing, updating, and deleting **client companies** (organizations we perform work for).

### FR-2: Client contacts
Each client company shall have **contacts** — people affiliated with that client. Contacts may optionally be linked to a system `user` account if they need to log in.

### FR-3: Project-client association
A project may be associated with one or more client companies via a `project_clients` join table. A client may have many projects. If a project has a single client it is displayed as "the client" in the UI.

### FR-4: Client participant access
Client contacts who have a linked system `user` account may be granted **project-level access** via a dedicated `project_client_access` table. This is separate from internal `project_members`.

### FR-5: Limited project visibility
Client participants shall see only:
- Project name, description, status, health badge
- Tasks and tickets assigned to them or their client company contacts
- Activity entries visible to client participants (no internal-only activities)
- A "Client view" toggle or separate route

### FR-6: Client contact management
Client contacts may manage other contacts within their own client company (add/update/remove) if they have a "contact_admin" role on the client.

### FR-7: Sales pipeline (prospects)
Sales leads are tracked as **prospects** (separate from clients). Each prospect has a `pipeline_stage` tracking the lifecycle: `target` → `connected` → `engaged` → `call_scheduled` → `call_done` → `proposal_sent` → `negotiating` → `won` → `lost`. Stages can only advance (except `lost`, which can come from any stage). `won` and `lost` are terminal. When a prospect reaches `won`, a corresponding `client` record is auto-created.

### FR-8: Pipeline automation flags
Based on stage and inactivity duration, the system shall surface automated flags (not auto-actions in V1):
- `connected` + no activity 7d → flag "send follow-up"
- `proposal_sent` + no activity 5d → flag "check-in"
- `proposal_sent` + no activity 10d → flag "breakup message"
- Any stage + no activity 30d → flag "review for lost"

### FR-9: Client referrers
The system shall track referrals: who referred a client, relationship type, and referral outcome.

### FR-10: Client onboarding checklist
When a prospect moves to `won` and a client is created, a default onboarding checklist shall be created on the client record (contract, deposit, kickoff, repo, channel, first milestone, etc.).

---

## 4. Non-functional requirements

### NFR-1: Permission isolation
Client participants must never see internal activity, internal notes, tasks assigned to team members only, or project settings. The system must enforce a hard boundary between internal `project_members` and client `project_client_access`.

### NFR-2: Backward compatibility
Existing projects (without `project_clients` rows) must continue to work exactly as before. Adding client associations via `project_clients` is optional and non-breaking.

### NFR-3: Idempotent schema
All new tables and columns must use `CREATE TABLE IF NOT EXISTS` / `ADD COLUMN IF NOT EXISTS` patterns consistent with the existing `sql/schema_*.sql` workflow.

### NFR-4: No plaintext secrets
Client tokens or external credentials (if any) must be encrypted at rest, following the Fernet pattern from `github_token_crypto.py`.

## 7. UI / UX

### Prospect list page (`/prospects`)
- Table with columns: company name, pipeline stage, primary contact, value, last interaction
- Filter by pipeline stage
- Stage transition dropdown per row
- Click → prospect detail

### Client list page (`/clients`)
- Table with columns: name, primary contact, projects count, created date
- Click → client detail

### Prospect detail page (`/prospects/[id]`)
- Header: company name, stage badge, source, value
- Tabs:
  - **Overview** — notes, next action, contacts
  - **Activity** — interaction log
  - **Referrals** — who referred this prospect
- Stage transition widget: dropdown with validation

### Client detail page (`/clients/[id]`)
- Header: name, industry tags
- Tabs:
  - **Overview** — notes
  - **Contacts** — list of client contacts, add/edit/remove
  - **Projects** — list of associated projects with health badges
  - **Onboarding** — checklist items

### Project page modifications
- Add "Client" section to project settings
- Client badge on project list and header when linked
- "Client access" tab in project settings (for internal team only)

### Client login (`/client/login`)
- Separate login page from internal `/login`
- After auth, redirects to limited client dashboard showing only accessible projects
- No access to internal pages, admin, settings

### Client participant project view
- Limited sidebar: only sees projects they have access to
- Project view: sees tasks assigned to them/their contacts, public activity
- No access to: project settings, member management, GitHub section, internal activities
- `view` role: read-only
- `contribute` role: can create tasks, comment

## 8. Permissions / roles

### Internal team (existing `project_members`)
| Role | Client management in project |
|------|------------------------------|
| `owner` | Full: link/unlink client, manage client access, see all |
| `maintainer` | Same as owner for client access |
| `contributor` | View client info, add comments to client-visible activities |
| `viewer` | View client info only |

### Client-side roles (new `project_client_access.role`)
| Role | What they see | What they can do |
|------|---------------|------------------|
| `view` (default) | Project health, public activity | Read-only |
| `contribute` | Tasks, tickets, public activity | Create tasks, comment |
| `decision_maker` | All tasks, tickets, public activity | Contribute + approve/reject proposals |
| `billing` | Project health, billing info | Read-only |

### Client-level roles (new, on `client_contacts`)
| Role | Scope |
|------|-------|
| `contact_admin` | Can manage contacts within their client company |
| `contact` | Can only view their own contact record |
