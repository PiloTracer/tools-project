# Multi-Tenancy — Feature SPEC

**Status:** Approved
**Owner:** Engineering
**Date:** 2026-07-06
**Slug:** multi-tenancy
**ADRs referenced:** ADR-0001 (client-contact model), ADR-0002 (backend stack: FastAPI, SQLAlchemy async), ADR-0004 (hosting/deployment)
**Related plans:** `.work/plans/NEXT.md` (post-ecosystem-hub), `.work/plans/foundation/20260618-04-architecture.md`

## 1. Purpose

Add row-level multi-tenancy to tools-project so multiple organizations can operate in a single deployment without seeing each other's data. Every user, project, prospect, client, and configuration row will belong to exactly one tenant. The existing project-scoped access control pattern (`require_project_access`) is retained; tenancy adds a higher-level isolation layer above it.

Today the system is single-tenant: `users` are global, `prospects` and `clients` are global (no project or org scope), and there is no `tenant_id` column anywhere in the 16-table schema. This SPEC defines the architecture to partition all data by tenant using a row-level isolation strategy (shared database, shared schema, `tenant_id` FK on every isolated table).

## 2. In scope / Out of scope

**In scope:**
- `tenants` table with UUID PK, slug (unique), name, settings JSONB, `is_active`
- `tenant_id` FK column on: `users`, `projects`, `prospects`, `clients`, `client_contacts`, `webhook_subscriptions`, `user_api_keys`
- JWT carries `tenant_id` claim; login resolves tenant from `users.tenant_id`
- `get_current_tenant` FastAPI dependency that resolves and caches tenant per request
- All CRM routers (prospects, clients, client_contacts, client_health) scoped to current tenant
- All admin routers (users, webhooks) scoped to current tenant
- Auth router: login resolves tenant; `GET /v1/auth/config` returns tenant info
- Unique constraint changes: `clients.slug` unique per tenant; `users.email` unique per tenant (not globally — same email can exist in different tenants)
- Backfill migration: create a default tenant, assign all existing rows, apply NOT NULL
- Cross-tenant leak test suite: every endpoint exercised as two tenants, asserting isolation
- Frontend: login page supports tenant selection (email-based resolution or subdomain); API client attaches tenant context
- Agent query API scoped to tenant (API keys are tenant-scoped; agent endpoints filter by tenant)

**Out of scope:**
- Schema-per-tenant or database-per-tenant isolation (remains row-level only)
- Tenant provisioning UI (admin creates tenants via CLI or DB for now)
- Per-tenant custom branding or theming
- Cross-tenant data sharing or "partner" relationships
- Tenant billing or usage quotas
- Self-service tenant signup
- Database connection pooling per tenant
- Row-level security (PostgreSQL RLS policies) — app-layer filtering only for this iteration

## 3. Domain language

| Term | Definition |
|------|------------|
| Tenant | An organization or workspace that owns a set of users, projects, clients, and prospects. All data is scoped to exactly one tenant. |
| Row-level tenancy | Isolation strategy where every row carries a `tenant_id` FK; the application enforces `WHERE tenant_id = ?` on every query. Single DB, single schema. |
| Default tenant | The tenant assigned to all existing rows during the backfill migration. Created with slug `default`. |
| Cross-tenant leak | A bug where one `WHERE` clause is missing and Tenant A sees Tenant B's data. The primary risk of row-level tenancy. |
| Cross-tenant superuser | A user with `is_superuser = true` and `tenant_id IS NULL` who can administer all tenants. Rare — typically 1–2 bootstrap accounts. |
| Org admin (per-tenant superuser) | A user with `is_superuser = true` and `tenant_id IS NOT NULL`. Full admin within their tenant only — cannot see or manage other tenants. |

## 4. Behavioural spec

### T1 — Tenant isolation (core invariant)

R1 — Every API request that reads or writes tenant-scoped data MUST resolve the current tenant and filter all queries by `tenant_id`. The only exceptions are: login (tenant is not yet known), health check, and the `GET /v1/auth/config` endpoint (returns available auth modes; may include tenant hint after login).

R2 — Tenant resolution priority: (1) subdomain (`{slug}.localhost`), (2) JWT `tenant_id` claim, (3) `X-Tenant-Slug` header (for API clients that can't set subdomains). The first match wins. If none resolve, the request is rejected with `401` unless on the allowlist (login, health, auth config).

R2a — Subdomain extraction: the middleware parses the `Host` header. For `{slug}.localhost` in dev (or `{slug}.{PUBLIC_HOST}` in production), `slug` is the tenant slug. For `localhost`/root domain or bare IP with no subdomain, fall through to JWT/header resolution.

R2b — `X-Tenant-Slug` header is accepted as a convenience for API clients and the MCP server. It is NOT trusted for auth — it only selects the tenant; the JWT or API key still carries the actual authorization.

R2c — When an API key (`X-Api-Key`) is present, the tenant is resolved from the key owner's `user.tenant_id`. An `X-Tenant-Slug` header, if present, MUST match the key owner's tenant; otherwise the request is rejected with `401` (treated as an invalid key for that tenant). API keys are tenant-scoped and cannot be used across tenants.

R3 — `get_current_tenant` loads the `Tenant` row, checks `is_active`, and caches it on `request.state` for the duration of the request. Inactive tenants receive `403` on all endpoints except login (where they receive a clear "account disabled" error).

### T2 — User model changes

R4 — Every `users` row belongs to exactly one tenant (`tenant_id NOT NULL`). The only exception is cross-tenant superusers (`tenant_id IS NULL`). Per-tenant superusers (org admins) have `is_superuser = true` AND `tenant_id IS NOT NULL` — they are full admins within their tenant only.

R4a — A cross-tenant superuser (`tenant_id IS NULL`) bypasses tenant scoping on all queries. They see all tenants' data. This is a bootstrap/admin escape hatch — there should be very few of these accounts.

R4b — A per-tenant superuser (`is_superuser = true`, `tenant_id IS NOT NULL`) has full CRUD within their tenant (manage users, webhooks, all project access) but cannot cross tenant boundaries. The `require_superuser` dependency checks both `is_superuser` AND tenant membership.

R4c — The bootstrap admin created by `app/bootstrap.py` when the database is empty is created as a **cross-tenant superuser** (`tenant_id IS NULL`) so it can administer all tenants. The default tenant is also created at bootstrap time, and the bootstrap admin is not assigned to it (consistent with R4a).

R5 — `users.email` is unique per tenant, not globally. The same email address can exist in two different tenants as two different user accounts.

R6 — `get_current_user` dependency is extended: after resolving the user, it stores `user.tenant_id` on `request.state` so downstream dependencies (`get_current_tenant`, `require_project_access`) can enforce tenant consistency without an extra DB round-trip.

R6a — If a JWT includes a `tenant_id` claim, it MUST match `user.tenant_id`. Mismatch results in `401` (token rejected). Cross-tenant superusers (`tenant_id IS NULL`) have no `tenant_id` claim in the JWT; their unbounded access is enforced by `user.tenant_id IS NULL`, not by a claim.

### T3 — Login and JWT

R7 — `POST /v1/auth/local/login` accepts `{ "email", "password" }` and an optional `tenant_slug`. Tenant is resolved from the request context (subdomain → header → JWT claim, per R2). If a tenant IS resolved (via subdomain), only users in that tenant are searched — no ambiguity.

If no tenant is resolved and the email/password pair is valid, the endpoint checks how many tenants contain that email. If exactly one, it logs the user into that tenant. If more than one, it returns `300 Multiple Choices` with a list of `{ "tenant_slug", "tenant_name" }` so the frontend can prompt the user to select. The password must be verified **before** returning tenant choices, so the endpoint does not leak tenant membership for unauthenticated emails (same 401 as wrong password).

R8 — On successful login, the JWT includes `sub` (user_id), `tenant_id`, and `is_superuser`. The access token TTL and refresh token behaviour are unchanged.

R9 — `GET /v1/auth/config` returns `multi_tenant: true` and `tenant` (resolved from subdomain, or null if no subdomain matched). The frontend uses this to show the tenant name in the login UI and to build tenant-scoped API URLs (`{slug}.localhost:8300`).

### T3-OAuth — Tenant resolution for OAuth / integrated auth

R9a — When `AUTH_OAUTH_ENABLED` is true, the OAuth callback may include a `tenant_slug` query parameter captured at sign-in kickoff. The callback handler resolves the tenant in the same priority order as R2: subdomain → `tenant_slug` param → `X-Tenant-Slug` header fallback.

R9b — If the OAuth userinfo email matches a single tenant, the user is resolved/upserted in that tenant. If it matches multiple tenants and no tenant context is provided, the callback returns the same `300 Multiple Choices` response as local login, listing only tenants where the email exists.

R9c — An OAuth sign-in for an unknown email is rejected with 401/403 (do not auto-provision across tenants). Tenant provisioning remains admin-only.

### T3-ClientPortal — Client portal tenant resolution

R9d — Client contacts log in through the same local/OAuth flows as internal users. The `/client/login` page resolves tenant via subdomain first (`{slug}.localhost/client/login`). If no subdomain is present, it falls back to `X-Tenant-Slug` or a tenant picker after the first authentication step.

R9e — A client contact's `client_contacts.user_id` links to a `users` row that already carries `tenant_id`. The client portal session is therefore tenant-scoped by the linked user record; client participants cannot switch tenants.

R9f — Client portal endpoints reuse `get_current_user` and `get_current_client_participant`; tenant consistency is enforced by the same `get_current_tenant` dependency as internal endpoints.

### T4 — Tenant-scoped CRUD

R10 — All existing `require_project_access` checks remain in place. They are augmented with a tenant-consistency check: the project's `tenant_id` must match `request.state.tenant_id`. Mismatch → `404` (not `403` — don't leak that the project exists in another tenant).

R11 — `GET /v1/projects` returns only projects where `tenant_id = current_tenant.id`. No other changes to the project list shape.

R12 — Prospects, Clients, ClientContacts, and ClientHealth endpoints gain `tenant_id` filtering on every query. Create operations set `tenant_id` from the current tenant. These routers previously had no tenant or project scope — they were truly global — so every endpoint in these four routers is touched.

R13 — Admin user management (`POST/GET/PATCH/DELETE /v1/admin/users`) is scoped to the current tenant. Per-tenant superusers (org admins, `is_superuser = true`, `tenant_id IS NOT NULL`) see and manage only their own tenant's users.

R13a — Cross-tenant superusers (`tenant_id IS NULL`) can list and modify users across all tenants. When a cross-tenant superuser creates a user (`POST /v1/admin/users`), the request body MUST include `tenant_id` or `tenant_slug` to specify the target tenant; otherwise the request returns `400`.

R14 — Webhook subscriptions (`/v1/admin/webhook-subscriptions`) are scoped to the current tenant. The `webhook_subscriptions` table gains `tenant_id`.

R14a — Every dispatched webhook payload includes `tenant_id` and `tenant_slug` at the top level so satellite apps can route events to the correct organization. The dispatcher loads subscriptions filtered by `tenant_id` and never delivers a tenant's events to a subscription belonging to another tenant.

R15 — Agent query API (`/v1/agent/*`) endpoints filter all project-scoped queries by tenant. API keys (`user_api_keys`) gain `tenant_id` — a key is always tenant-scoped. Cross-tenant superuser API keys are not supported (superusers get a regular tenant-scoped key for agent access).

### T5 — Data integrity

R16 — Creating a project under a tenant sets `projects.tenant_id = current_tenant.id`. All child rows (tasks, tickets, activities, attachments, github_links, components, project_members, project_clients) inherit tenant isolation through the project FK chain — they do not need their own `tenant_id` column, but every query that joins to `projects` must include `AND projects.tenant_id = ?`.

R16a — Cross-tenant superusers creating a project, client, or prospect MUST provide `tenant_id` or `tenant_slug` in the request body, because they have no implicit tenant. Regular users and per-tenant admins use their own tenant.

R17 — Creating a client under a tenant sets `clients.tenant_id = current_tenant.id`. Client contacts inherit tenant through `client_id`. Prospects inherit tenant from `created_by` user's tenant or explicit `tenant_id`.

R18 — Tenant deletion is soft (`tenants.is_active = false`). Hard deletion is out of scope. A deactivated tenant blocks all logins and API access for that tenant's users.

## 5. Data model

### New table: `tenants`

```sql
CREATE TABLE IF NOT EXISTS tenants (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    slug VARCHAR(50) NOT NULL,
    name VARCHAR(200) NOT NULL,
    settings JSONB NOT NULL DEFAULT '{}',
    is_active BOOLEAN NOT NULL DEFAULT true,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE UNIQUE INDEX IF NOT EXISTS uq_tenants_slug ON tenants (slug);
```

### Columns to add

| Table | New column | Nullable | FK | Notes |
|-------|-----------|----------|-----|-------|
| `users` | `tenant_id` | NULLable (NOT NULL for regular users) | `tenants.id` | Cross-tenant superusers have `tenant_id IS NULL`; per-tenant superusers (org admins) have `tenant_id IS NOT NULL` |
| `projects` | `tenant_id` | NOT NULL | `tenants.id` | Set from `current_tenant` on create |
| `prospects` | `tenant_id` | NOT NULL | `tenants.id` | Set from `current_tenant` on create |
| `clients` | `tenant_id` | NOT NULL | `tenants.id` | Set from `current_tenant` on create |
| `client_contacts` | `tenant_id` | NOT NULL | `tenants.id` | Denormalized from clients for query perf; set on create |
| `webhook_subscriptions` | `tenant_id` | NOT NULL | `tenants.id` | Set from `current_tenant` on create |
| `user_api_keys` | `tenant_id` | NOT NULL | `tenants.id` | Set from key owner's `tenant_id` on create |

### Unique constraint changes

| Constraint | Old | New |
|-----------|-----|-----|
| `users.email` | `UNIQUE` globally | `UNIQUE (email, tenant_id)` — same email allowed in different tenants |
| `clients.slug` | `UNIQUE` globally | `UNIQUE (slug, tenant_id)` |
| `users.email` (superuser path) | — | Superusers with `tenant_id IS NULL` still have globally unique emails (partial unique index) |
| `users.tenant_id` | — | `CHECK (is_superuser = true OR tenant_id IS NOT NULL)` — regular users must belong to a tenant; cross-tenant superusers may be NULL |

### Tables that DO NOT get `tenant_id` (inherit via FK chain)

These tables are project-scoped and inherit tenant isolation through `projects.tenant_id`. Queries must join `projects` and filter `projects.tenant_id`, but no new column is needed:

`tasks`, `tickets`, `activities`, `attachments`, `mentions`, `components`, `project_members`, `project_clients`, `project_client_access`, `project_counters`, `github_links`, `github_commits`, `commit_subject_refs`, `inbox_items`, `watchers`

### Migration constraints

- **Applied on restart only** — no direct/adhoc backfills. All DDL runs through `sql/schema_changes.sql` → `sql/schema_indexes.sql` → `sql/schema_backfill.sql` → `sql/schema_inserts.sql` on API startup, per the existing `schema_sql.py` runner.
- **Idempotent** — every statement uses `IF NOT EXISTS` / `IF EXISTS` / `ADD COLUMN IF NOT EXISTS`. Re-running N times produces the same result.
- **Backfills are idempotent** — `UPDATE ... SET tenant_id = (SELECT id FROM tenants WHERE slug = 'default') WHERE tenant_id IS NULL` is safe to re-run; rows already assigned are skipped.
- **No destructive DDL** — columns are added nullable first, backfilled, then constrained. No `DROP COLUMN`, no `ALTER COLUMN ... TYPE`.

### Migration order

1. `tenants` table — `CREATE TABLE IF NOT EXISTS`
2. Default tenant row — `INSERT INTO tenants (slug, name) VALUES ('default', 'Default Organization') ON CONFLICT DO NOTHING`
3. `tenant_id` columns added nullable — `ALTER TABLE ... ADD COLUMN IF NOT EXISTS tenant_id UUID REFERENCES tenants(id)`
4. Backfill existing rows — `UPDATE {table} SET tenant_id = (SELECT id FROM tenants WHERE slug = 'default') WHERE tenant_id IS NULL` per table, idempotent
5. `users` `CHECK` constraint — `CHECK (is_superuser = true OR tenant_id IS NOT NULL)` (allows cross-tenant superusers to remain NULL while requiring regular users to have a tenant)
6. NOT NULL constraints — `ALTER TABLE ... ALTER COLUMN tenant_id SET NOT NULL` on all non-`users` tables (only after backfill confirms no NULLs remain; fails safe if any row missed)
7. Create FKs to `tenants.id` where not already created by `REFERENCES` in step 3
8. Drop old global unique constraints, create per-tenant ones — `DROP INDEX IF EXISTS` / `CREATE UNIQUE INDEX IF NOT EXISTS`
9. Create indexes on `tenant_id` for all target tables

### Subdomain routing

Tenant context is resolved from the `Host` header. Two deployment shapes are supported:

**Production / Caddy mode (single ingress):** Caddy routes by host and path. API traffic uses the `api.` subdomain prefix so web and API do not collide on the same hostname.

```caddy
# Tenant-scoped API
api.{$PUBLIC_HOST}, *.{$PUBLIC_HOST} {
    @api path /v1/* /docs /openapi.json /healthz
    handle @api {
        reverse_proxy api:8300
    }
}

# Tenant-scoped web
*.{$PUBLIC_HOST} {
    handle {
        reverse_proxy web:3000
    }
}

# Root domain — no tenant context, used for login when tenant unknown
{$PUBLIC_HOST} {
    handle {
        reverse_proxy web:3000
    }
}
```

**Development / separate-ports mode:** The existing dev stack keeps web on `${WEB_DEV_HOST_PORT:-18513}` and API on `${API_HOST_PORT:-8300}`. In this mode the web BFF (`web/src/app/api/*`) injects `X-Tenant-Slug` based on the requested host or a session cookie, and the API resolves tenant from the header instead of the subdomain. This preserves the current `docker-compose.dev.yml` port layout.

The API resolves the tenant slug from `Host` header first, then falls back to `X-Tenant-Slug`. Web reads tenant from `GET /v1/auth/config` response and constructs API URLs with the correct subdomain in production, or sends `X-Tenant-Slug` in development.

### Subdomain deployment considerations

R9g — Session cookies (`prj_auth` / `prj_refresh`) MUST be set with `Domain={PUBLIC_HOST}` (e.g., `Domain=localhost` in dev) so they are sent to all tenant subdomains. Cookie `Path=/` and `SameSite=Lax` remain unchanged; `secure` is enabled in production (HTTPS only).

R9h — `CORS_ALLOWED_ORIGINS` MUST include the root origin and all tenant subdomains (`http://*.localhost:18513` or equivalent), or the web app on `tenant.localhost` cannot call the API on `api.tenant.localhost`. In development, the web BFF path avoids CORS by proxying; in production Caddy handles the same origin. If direct browser-to-API calls are used, CORS must be configured.

R9i — `PUBLIC_ORIGIN` becomes tenant-aware. The web app must build OAuth redirect URIs and absolute URLs using the current tenant's host (`{slug}.{PUBLIC_HOST}`), not a single static origin. Server components can derive this from the incoming request host; client components receive it via `GET /v1/auth/config`.

R9j — `api.{slug}.localhost` and `{slug}.localhost` share the same session cookie. Logging out on one clears the cookie for all subdomains of the same root domain.

R9k — The external OAuth IdP (tools-dashboard) must accept redirect URIs for all tenant subdomains (`http://*.{PUBLIC_HOST}:{WEB_DEV_HOST_PORT}/oauth/complete` in dev, `https://*.{PUBLIC_HOST}/oauth/complete` in production). If the IdP does not support wildcard redirect URIs, tenant provisioning must include registering each tenant's redirect URI.

## 7. Invariants

- Two users in different tenants can never access each other's projects, prospects, clients, or any other data.
- A user's `tenant_id` is immutable after creation (reassigning a user to a different tenant requires admin CLI/DB intervention, not API).
- A project's `tenant_id` is immutable after creation.
- Every query against a tenant-scoped table includes `WHERE tenant_id = ?` or joins through a table that already filters by tenant.
- The backfill migration assigns every existing row to the default tenant — no data is orphaned.
- Login for an email existing in N tenants returns N choices only after the password is verified; the user must pick one.
- API keys are tenant-scoped; a key from tenant A cannot authenticate requests as tenant B.

## 8. Error model

| Code | Condition | Response |
|------|-----------|----------|
| 300 | Authenticated login where email exists in multiple tenants and no tenant resolved via subdomain | `{ "choices": [{ "tenant_slug", "tenant_name" }] }` |
| 401 | No tenant resolved (no subdomain, no JWT claim, no header) on a tenant-scoped endpoint | `{ "detail": "Tenant context required" }` |
| 401 | JWT `tenant_id` claim does not match user's `tenant_id` | `{ "detail": "Invalid token" }` |
| 401 | API key's owner tenant does not match `X-Tenant-Slug` header | `{ "detail": "Invalid API key for tenant" }` |
| 403 | Tenant is inactive | `{ "detail": "Organization account is disabled" }` |
| 403 | Valid JWT, valid tenant, but user's tenant doesn't match resource | Return **404** instead (don't leak resource existence) |
| 404 | Resource not found in current tenant (tenant mismatch or genuinely missing) | Standard 404 — indistinguishable from missing |
| 422 | `tenant_slug` provided but no user with that email in that tenant | `{ "detail": "Invalid email or password" }` — same as wrong password (don't leak tenant membership) |
| 400 | Cross-tenant superuser creates user/project/client/prospect without `tenant_id`/`tenant_slug` | `{ "detail": "tenant_id or tenant_slug is required" }` |

## 9. Observability

- Every request logs `tenant_id` (or `tenant_id=none` for unauthenticated/health endpoints)
- Counter metric: `tenant_requests_total{tenant_id, status}` — per-tenant request volume
- Counter metric: `tenant_auth_ambiguous_total` — login attempts where email matched multiple tenants
- Log warning when a query is executed without a `tenant_id` filter on a tenant-scoped table (best-effort detection via query logging or SQLCommenter-style tagging)
- Existing request ID middleware and structured logging are unchanged

## 10. Security and privacy

- Row-level isolation enforced at the application layer. PostgreSQL RLS policies are not used in this iteration but remain an available defense-in-depth upgrade path.
- Cross-tenant superusers (`tenant_id IS NULL`) are the only accounts that span tenants. Their count should be minimal (ideally 1–2 bootstrap admins). All other users are tenant-scoped.
- The `tenant_id` claim in the JWT is signed and cannot be tampered with by the client (standard HMAC/RSA JWT enforcement).
- Login responses must not leak whether an email exists: wrong password, wrong tenant, and nonexistent email all return the same 401 message.
- `300 Multiple Choices` on ambiguous login is returned only after the password has been verified, so it does not leak tenant membership for unauthenticated emails. The tradeoff is acceptable because the set of tenants is revealed only to a user who already proved ownership of the email.
- Superuser endpoints (tenant CRUD) must be behind `require_superuser` AND the cross-tenant superuser check (`tenant_id IS NULL`). Org admins cannot create or modify tenants.

| Test | Method |
|------|--------|
| User A (tenant-1) lists projects — no tenant-2 projects returned | Create 2 tenants, 1 project each. GET as tenant-1 user, assert only tenant-1 project |

## 12. Rollout and rollback

### Rollout

1. Deploy migration (steps in §5). System remains operational during backfill (`tenant_id` columns are nullable until step 6).
2. Deploy API changes with new dependencies and tenant filters.
3. Deploy frontend changes with tenant selection on login.
4. Existing users log in — they're all in the `default` tenant. No UX change for single-tenant deployments.
5. Create additional tenants via CLI or DB insert.

### Rollback

Rollback is **destructive** after the `NOT NULL` constraint is applied (step 6 of migration). To roll back:

1. Drop `NOT NULL` constraints on all `tenant_id` columns.
2. Set all `tenant_id` values to NULL.
3. Drop `tenant_id` columns.
4. Drop `tenants` table.
5. Restore old unique constraints.
6. Deploy previous API version.

**Recommendation:** test the migration thoroughly in a staging environment before production. Take a database snapshot before running the migration. The `NOT NULL` application step is the point of no return.

### Feature flag

A `MULTI_TENANCY_ENABLED` env var (default `false`) gates the tenant dependency injection. When `false`, `get_current_tenant` returns the default tenant silently and JWTs do not require a `tenant_id` claim. This allows the code to ship without immediately enforcing tenancy — existing single-tenant deployments are unaffected. Flip to `true` when ready to enforce.

## 13. Open questions

All resolved.

1. **Email global uniqueness vs per-tenant:** ✅ **Per-tenant.** Same email can exist in different tenants as different accounts.
2. **Cross-tenant superuser model:** ✅ **Dual model.** `tenant_id IS NULL` = cross-tenant superuser; `is_superuser=true` + `tenant_id IS NOT NULL` = per-tenant org admin.
3. **Default tenant name:** ✅ **Hardcoded "Default Organization".** No env var complexity needed — single-tenant deployments get this name and never see it in the UI.
4. **Agent API key tenant scope:** ✅ **Tenant-scoped.** API keys are locked to a single tenant. No cross-tenant agent access. Cross-tenant superusers who need agent access create a key per tenant.
5. **Subdomain routing:** ✅ **Yes.** `{slug}.localhost` (dev) / `{slug}.{PUBLIC_HOST}` (prd). Resolution: subdomain → JWT `tenant_id` → `X-Tenant-Slug` header. Dev fallback: web BFF injects `X-Tenant-Slug` when separate API/web ports are used.
6. **Client portal multi-tenancy:** ✅ **Resolved by subdomain routing.** `{tenant}.localhost/client/login`.

## 15. Concept / NFR registry

| Concept id | Applies | Notes |
|------------|---------|-------|
| MOD-01 | yes | Multi-tenancy is a cross-cutting architectural change — touches auth, every router, the data model, and deployment |
| MOD-02 | no | No AI-assisted PR review in this scope |

| MOD-05 | yes | Data isolation between tenants is a compliance-sensitive concern — cross-tenant leak is a reportable incident if this system handles client data |
