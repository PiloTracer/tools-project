# RFP Award Webhook — Feature SPEC

**Status:** Approved
**Owner:** Engineering
**ADRs referenced:** ADR-0001 (client-contact model), ADR-0002 (backend stack: FastAPI, SQLAlchemy async)
**Related plans:** `proposal_tools_project_ecosystem_hub` (Modification 4)

## 1. Purpose

Accept an authenticated webhook call from `tools-rfp` when an RFP is awarded, convert it into a `tools-project` Prospect, transition it to `won`, and trigger the already-shipped prospect-to-client promotion pipeline (`promote_prospect_to_client` + `auto_scaffold_onboarding_project`). This is the single integration point between the RFP tracking app and the CRM/PM hub — 95% of the automation already exists on the receiving side.

## 2. In scope / Out of scope

**In scope:**
- One new endpoint: `POST /v1/integrations/rfp/award`
- HMAC-SHA256 signed payload verification using a shared secret
- `webhook_secrets` table (or reuse existing encrypted-token pattern) for managing shared secrets per integration
- Resolve or create a `Prospect` from the RFP data (company name, contact email)
- Transition prospect to `won` and run existing promotion pipeline
- Return `201` with project + client details on success
- Structured error responses for invalid signature, duplicate processing, missing fields
- Idempotency key support (`X-Idempotency-Key`) to prevent duplicate processing

**Out of scope:**
- Outbound webhook dispatcher (Modification 1 — separate feature)
- Platform identity / whoami endpoint (Modification 2 — separate feature)
- Cross-app reference table (Modification 3 — separate feature)
- OAuth2 provider (explicitly deferred by proposal)
- Subscription management UI (secrets configured via env or CLI, not web UI)
- Retry/delivery guarantees on the `tools-rfp` side (handled by the caller)

## 3. Domain language

| Term | Definition |
|------|------------|
| RFP Award | A notification from `tools-rfp` that a submitted RFP response has been selected/won |
| Webhook secret | HMAC-SHA256 shared key used to sign and verify webhook payloads between `tools-rfp` and `tools-project` |
| Idempotency key | Client-supplied UUID that ensures the endpoint processes a given RFP award exactly once |
| Integration route | A `/v1/integrations/` prefixed endpoint, distinct from core API routes, for cross-app communication |

## 4. Behavioural spec

R1 — The endpoint `POST /v1/integrations/rfp/award` accepts a JSON body with `X-Webhook-Signature` and `X-Idempotency-Key` headers.

R2 — The signature is computed as `HMAC-SHA256(body, secret)` and compared constant-time. Request is rejected with `401` on mismatch.

R3 — If `X-Idempotency-Key` has been seen before (stored in a small `integration_idempotency` table), return the previous `201` response without re-processing. Expire keys after 24 hours.

R4 — The payload contains: `{ "company_name", "contact_email", "contact_name"?, "rfp_title"?, "rfp_url"? }`. Only `company_name` and `contact_email` are required.

R5 — Resolve the `contact_email` against existing `client_contacts.email`. If found, use that contact. If not found, create a new `Prospect` with the provided data.

R6 — Transition the prospect to `won` using the existing stage validation pipeline (`api/app/routers/prospects.py` stage transition logic).

R7 — Run `pipeline_service.promote_prospect_to_client()` and `auto_scaffold_onboarding_project()` — these are the already-shipped functions that create the client record, onboarding project, 7 tasks, and access grants.

R8 — Return `201` with `{ "client_id", "client_name", "project_id", "project_name", "prospect_id" }`.

R9 — Errors: `401` (bad signature), `409` (already processed — idempotency conflict with different payload), `422` (validation), `500` (pipeline failure, with logged details).

## 5. Data model

New table `integration_secrets` (or extend pattern from `github_links`):

```sql
CREATE TABLE IF NOT EXISTS integration_secrets (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    source_app VARCHAR(30) NOT NULL,
    key_hash VARCHAR(64) NOT NULL,
    key_prefix VARCHAR(8) NOT NULL,
    label VARCHAR(100),
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    revoked_at TIMESTAMPTZ
);
CREATE UNIQUE INDEX IF NOT EXISTS uq_integration_secrets_key_hash ON integration_secrets (key_hash);
```

New table `integration_idempotency`:

```sql
CREATE TABLE IF NOT EXISTS integration_idempotency (
    idempotency_key VARCHAR(64) PRIMARY KEY,
    response_status INTEGER NOT NULL,
    response_body TEXT NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

Or simplify: store the webhook secret in `Settings` (config env var) for V1, avoiding a new table until multiple integration sources exist. **Recommended for V1:** single env var `RFP_WEBHOOK_SECRET` + in-memory idempotency dict (process-local; restart resets — acceptable for MVP since `tools-rfp` can retry).

## 6. APIs

### `POST /v1/integrations/rfp/award`

**Headers:**
- `Content-Type: application/json`
- `X-Webhook-Signature: sha256=<hex>` — HMAC-SHA256 of the raw request body
- `X-Idempotency-Key: <uuid>` — optional, prevents duplicate processing

**Request body:**
```json
{
  "company_name": "Acme Corp",
  "contact_email": "owner@acme.com",
  "contact_name": "Jane Doe",
  "rfp_title": "Website redesign RFP",
  "rfp_url": "https://rfp.example.com/123"
}
```

**Response `201`:**
```json
{
  "client_id": "uuid",
  "client_name": "Acme Corp",
  "project_id": "uuid",
  "project_name": "Acme Corp — Onboarding",
  "prospect_id": "uuid"
}
```

**Error responses:**
- `401`: `{ "detail": "Invalid signature" }`
- `409`: `{ "detail": "Idempotency key already processed with different payload", "existing_client_id": "uuid" }`
- `422`: `{ "detail": [...] }` (validation errors)

## 7. Invariants

- A webhook call with a valid signature always produces at most one client + one onboarding project.
- `contact_email` deduplication: the same email always maps to the same contact/client on subsequent calls.
- Idempotency keys guarantee exactly-once processing within the expiry window.
- No changes to any existing `tools-project` feature or data model (purely additive).

## 8. Error model

| Code | Condition | Behaviour |
|------|-----------|-----------|
| 401 | `X-Webhook-Signature` missing or invalid | Log source IP/prefix; return generic "Invalid signature" |
| 409 | Idempotency key collision with different body | Return stored response + conflict detail |
| 422 | Missing `company_name` or `contact_email` | Standard FastAPI validation error |
| 500 | `pipeline_service` raises unexpectedly | Log full traceback; return generic server error |

## 9. Observability

- One log line per webhook call: `rfp_webhook.received` (source app, company, result)
- One counter metric per outcome: `rfp_webhook_process{status=created|duplicate|error}`
- Track processing latency: `rfp_webhook_duration_seconds`
- Existing `activity_writer` already logs the promotion events — no additional instrumentation needed for the downstream pipeline

## 10. Security and privacy

- HMAC-SHA256 signing with a shared secret (not a full OAuth2 flow — appropriate for server-to-server within the same ecosystem)
- Secret configured via env var `RFP_WEBHOOK_SECRET` (same pattern as `AGENT_API_KEY` and `GITHUB_TOKEN_ENCRYPTION_KEY`)
- No PII in webhook error responses
- `contact_email` stored in `prospects` / `client_contacts` as per existing data model (already subject to DB encryption considerations)
- Idempotency keys stored with 24h TTL, then pruned

## 11. Test plan

| Test | Scope | Method |
|------|-------|--------|
| Valid webhook creates prospect + promotes | Integration | POST with valid signature → assert 201, assert prospect, client, project exist |
| Invalid signature rejected | Unit | POST with bad signature → assert 401 |
| Missing required fields | Unit | POST missing `company_name` → assert 422 |
| Idempotency key dedup | Integration | POST twice with same key → first 201, second 201 (same response), one prospect created |
| Duplicate email uses existing contact | Integration | POST twice with same email → second call reuses existing prospect/contact |
| Pipeline failure handled gracefully | Unit | Mock `pipeline_service` to raise → assert 500, no side effects |

## 12. Rollout and rollback

- Additive only — no existing code changes. Rollback: remove the router import from `main.py` and the migration.
- The webhook secret is configured via env var; toggle off by removing/rotating the secret.
- Feature flag: not needed — the endpoint is passive (no calls unless `tools-rfp` is configured to send them).

## 13. Open questions

- Should the webhook secret be a single env var (simpler) or a `integration_secrets` table (scalable to multiple source apps)? **Recommendation:** env var for V1, table when Mod 1 adds multiple integration sources.
- Should we use in-memory idempotency (lost on restart, simpler) or a DB-backed store (durable, more complex)? **Recommendation:** in-memory with a log warning on restart about potential re-processing — acceptable for MVP since `tools-rfp` retries are safe.
